# 06 养发直营连锁ERP系统角色权限模型 V10

**项目名称：** 养发直营连锁ERP自主研发项目
**版本：** V10
**前置文档：** 01～05
**文档定位：** 定义系统用户身份、岗位、角色、功能权限、数据权限、业务操作权限及审批权限。

---

# 一、权限体系总体目标

ERP权限系统解决的不只是：

> “这个人能不能看到这个菜单？”

而是完整解决：

```Plain Text
谁
 ↓
以什么身份
 ↓
在哪个门店
 ↓
可以看到哪些数据
 ↓
可以操作什么功能
 ↓
可以执行什么业务动作
 ↓
需要不需要审批
 ↓
可以处理到什么金额/范围
```

---

# 二、权限模型总体架构

系统采用：

# RBAC  数据权限  业务权限

三层结合。

```Plain Text
员工
 ↓
岗位
 ↓
角色
 ↓
功能权限
 ↓
数据权限
 ↓
业务权限
 ↓
审批权限
```

# 三、员工、用户、角色、岗位的关系

必须先把四个概念区分开。

---

## 31 员工 Employee

表示：

> 公司真实存在的人。

例如：

```Plain Text
张三
员工编号：E001
岗位：护理师
```

---

## 32 用户 User

表示：

> 这个员工用于登录ERP的系统账号。

一个员工通常对应一个登录用户。

但是员工和用户不要在代码/业务层混成一个对象。

---



## 33 岗位 Job

代表：

> 这个员工在组织中的职务。

例如：

```Plain Text
店长
护理师
顾问
前台
运营
财务
```

岗位主要参与：

- 默认角色；
- 数据范围；
- 绩效规则；
- 提成规则。

---



## 34 角色 Role

代表：

> 系统里这个人可以做什么。

例如：

```Plain Text
门店店长
前台收银
护理师
总部运营
总部财务
```

---



# 四、推荐的权限结构

最终：

```Plain Text
Employee
   ↓
User
   ↓
Role
   ↓
Permission
   ├── Menu
   ├── Page
   ├── Button
   └── API/Action
```

同时：

```Plain Text
Role
   ↓
DataScope
```

以及：

```Plain Text
Role
   ↓

```

V1建议建立以下基础角色。

```Plain Text
01 总部超级管理员
02 总部运营
03 总部财务
04 总部人事/绩效
05 区域负责人
06 门店店长
07 门店前台
08 顾问
09 护理师
10 库管
11 门店财务/出纳
```

不建议一开始建立几十个角色。

角色应该尽可能稳定。

如果某个员工只需要特殊权限：

> 用“附加权限”解决。

# 二十一、API权限

最终不能只靠前端隐藏按钮。

例如：

```Plain Text

```

```Plain Text

+

+
permission
+
store
+
```

# 三十一、会员账户人工调整权限

这是系统最高风险之一。

比如：

```Plain Text

赠金+300
次卡+1
```

原则上：

> 普通门店员工不得拥有。

建议：

```Plain Text
总部运营/管理员
 ↓
申请
 ↓
审核
 ↓
执行
```

并必须：

```Plain Text
填写原因
```

# 三十九、API层必须再次校验数据权限

例如员工请求：

```Plain Text
GET /customers/{id}
```

不能因为有：

```Plain Text
customer:view
```

就直接返回。

还必须判断：

```Plain Text
这个客户
是否属于这个员工允许的数据范围？
```

因此权限判断至少有两层：

```Plain Text
功能权限
+
数据权限
```

# 四十、权限校验统一模型

后端建议统一形成：

```Plain Text
PermissionContext
{
    userId,
    employeeId,
    roleIds,
    currentStoreId,
    dataScope,
    permissions
}
```

每个业务请求进入Service之前：

```Plain Text
身份校验
 ↓
功能权限
 ↓
门店权限
 ↓
数据权限
 ↓
业务规则
 ↓
执行
```

# 四十一、典型场景：前台退款

前台点击：

> 申请退款。

系统：

```Plain Text
登录身份
 ↓
前台角色
 ↓
是否有refund:create
 ↓
当前门店权限
 ↓
订单是否属于当前门店
 ↓
订单是否允许退款
 ↓
退款金额是否超过自己的权限范围
 ↓
创建退款申请
```

最终：

> 可以提交，但不能自己批准和执行。

---



# 四十二、典型场景：护理师耗卡

```Plain Text

 ↓

 ↓

 ↓
```

```Plain Text
是否允许使用该权益

是否过期

权益
是否有余额

是否超出
```

# 四十四、超级管理员也不能绕过业务规则

这一点非常重要。

超级管理员：

> 可以拥有最高权限。

但不能让：

```Plain Text
余额
库存
业绩
```

直接出现不可追溯的修改。

超级管理员做人工调整，也必须：

```Plain Text
原因
操作人
时间
调整前
调整后
```

# 四十八、权限与业务规则的关系

权限系统不是业务规则的替代品。

例如：

员工有：

```Plain Text
refund:create
```

不代表：

> 所有订单都能退款。

还必须经过：

```Plain Text
退款业务规则
+
订单状态
+
退款金额限制
+
账户状态
+
当前门店
```

所以：

```Plain Text
权限
决定“有没有资格尝试”

业务规则
决定“这笔业务是否允许”
```

这是开发时非常关键的边界。
