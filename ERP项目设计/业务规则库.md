**项目名称：** 养发直营连锁ERP自主研发项目
**文档版本：** V1\.0
**前置文档：** 01产品总体架构、02业务领域模型、03功能模块设计、04核心业务流程

# 一、业务规则库的作用

本规则库作为以下人员的共同标准：

```Plain Text
产品经理
项目负责人
开发人员
测试人员
运营人员
财务
门店负责人
BI人员
```

当出现业务争议时：

> **优先以本规则库为准。**
> 
> 

如原系统规则与本规则库存在差异：

```Plain Text
第一优先：
公司正式业务规则

第二优先：
当前门店实际执行规则

第三优先：
旧系统实际行为

第四优先：
程序设计人员自行判断
```

程序员不得自行发明业务规则。

---

# 二、规则编号体系

建议规则统一编号：

```Plain Text
ORG-组织规则
CUS-客户规则
PRO-商品项目规则
CAR-卡项权益规则
SAL-销售规则
PAY-支付规则
TRT-消耗规则
SRV-服务规则
INV-库存规则
PER-业绩规则
COM-提成规则
REF-退款规则
APP-预约规则
FIN-结算规则
SYS-系统规则
```

例如：

```Plain Text
CAR-001
储值卡本金可跨店

COM-005
销售提成采用超额累进

TRT-003
耗卡不产生新的现金支付
```

# 三、组织与门店规则

# ORG\-001 门店是经营业务最基本的业务主体

所有主要经营业务必须记录发生门店：

```Plain Text
销售
支付
消耗
服务
库存
退款
预约
业绩
对账
```

---

# ORG\-002 一个客户可以在多个直营门店发生业务

例如：

```Plain Text
A店办卡
B店耗卡
C店继续耗卡
```

不需要进行客户“转卡”。

---

# ORG\-003 会员权益跨店规则由权益类型决定

不能简单规定：

> 所有卡都跨店。
> 
> 

而应该由不同权益的业务规则判断。

当前已确认：

---

# ORG\-004 门店与客户归属不是同一个概念

以下概念必须分开：

```Plain Text
客户首次来源门店
客户归属门店
客户当前维护门店
客户本次消费/消耗门店
客户办卡门店
```

不得用一个字段全部替代。

---

# ORG\-005 员工可以存在历史门店关系

员工调店以后：

> 历史业务仍归属于当时的员工和当时门店。
> 
> 

不能通过更新员工当前门店而改变历史数据。

---

# ORG\-006 业务操作必须校验门店权限

员工进入系统时必须拥有：

```Plain Text
当前员工
+
当前门店
+
当前角色
+
当前功能权限
```

才能执行对应业务。

---

# 四、客户规则

# CUS\-001 Customer是客户唯一业务主体

客户即使没有办卡，也必须可以建档。

---

# CUS\-002 客户不能因为跨店而重复建立

搜索手机号、客户编号等识别信息时：

> 优先查全局客户。
> 
> 

而不是只查当前门店。

---

# CUS\-003 客户首次来源与本次来源分开

例如：

```Plain Text
首次来源：
美团

本次活动来源：
员工转介绍
```

不能覆盖首次来源。

---

# CUS\-004 客户可以没有会员权益

以下情况都属于合法客户：

```Plain Text
普通新客
体验客户
已耗尽卡项的老客户
沉睡客户
```

所以：

> 客户 ≠ 有卡会员。
> 
> 

---

# CUS\-005 客户归属人员与本次服务人员分开

例如：

```Plain Text
归属顾问：张三
本次护理师：李四
```

不能混为一人。

---

# CUS\-006 客户档案修改必须留痕

重点字段：

```Plain Text
姓名
手机号
来源
归属人员
会员等级
```

修改应能够查询操作人和时间。

---

# 五、商品规则

# PRO\-001 产品与项目必须区分

产品：

> 实物商品。
> 
> 

项目：

> 服务行为。
> 
> 

---

# PRO\-002 产品可以参与库存

例如：

```Plain Text
洗发水
精华液
养护产品
```

---

# PRO\-003 项目可以拥有耗材规则

例如：

```Plain Text
项目A
 →
精华液10ml
```

项目服务完成以后可以形成库存消耗。

---

# PRO\-004 商品基础价格与订单成交价格分离

商品配置：

```Plain Text
标准价格
```

销售订单：

```Plain Text
实际成交价格
```

不能因为历史订单发生改价而修改商品基础价格。

---

# PRO\-005 历史订单必须保存成交快照

至少：

```Plain Text
商品名称
项目名称
成交单价
数量
原价
优惠
```

后续商品改名、改价不能影响历史订单。

---

# PRO\-006 未来价格修改不能影响已售卡项

尤其：

```Plain Text
套餐
储值卡
次卡
时效卡
```

历史销售需要保留销售时规则。

---

# 六、储值卡规则

这是第一批最高优先级规则。

---

# CAR\-001 储值卡由本金与赠金组成

系统必须区分：

```Plain Text
本金余额
赠金余额
```

不能只有一个总余额。

---

# CAR\-002 本金可以跨直营门店使用

例如：

```Plain Text
A店充值
B店消耗
```

本金允许。

---

# CAR\-003 赠金不能跨店使用

例如：

```Plain Text
A店充值赠金
B店耗卡
```

赠金不可用。

系统必须在消耗提交时校验：

```Plain Text
account_store
consume_store
bonus_usage_rule
```

---

# CAR\-004 储值卡默认有效期三年

从正式生效日起计算。

具体起算点：

> V1建议按照销售完成/账户生成日期执行。
> 
> 

如果旧系统实际规则不同，在07数据兼容和上线前校准。

---

# CAR\-005 储值卡到期后小程序不可见

到期后：

```Plain Text
小程序：
隐藏/不可用

门店后台：
可以查询

授权员工：
可以延期
```

---

# CAR\-006 延期必须形成记录

必须记录：

```Plain Text
原有效期
新有效期
延期天数
操作人
操作时间
延期原因
```

---

# CAR\-007 储值赠金不能退款

无论：

```Plain Text
赠金剩余多少
```

原则上：

> 赠金本身不形成可退金额。
> 
> 

但若套餐/充值整体存在特殊退款规则，需要在退款规则中单独处理。

---

# CAR\-008 储值抵扣来源由护理师选择

护理师进行耗卡时：

```Plain Text
本金
赠金
混合
```

由操作人员选择。

系统不能默认强制：

> 本金优先。
> 
> 

---

# CAR\-009 混合抵扣必须拆开记录

例如：

```Plain Text
项目300

本金100
赠金200
```

系统必须知道：

```Plain Text
本金减少100
赠金减少200
```

不能只记录：

```Plain Text
储值减少300
```

---

# CAR\-010 储值余额不能直接修改

以下行为禁止：

```Plain Text
直接修改账户余额
```

所有余额变化必须有：

```Plain Text
业务来源
业务单号
流水
操作人
前后余额
```

---

# CAR\-011 余额变化必须可追溯

至少能够回答：

> 为什么这个客户今天少了300？
> 
> 

例如：

```Plain Text
消耗单T202608260001
项目：养发A
来源：储值本金
金额：300
护理师：李四
门店：B店
```

---

# 七、套餐卡规则

# CAR\-020 套餐卡是组合权益

套餐可以包含：

```Plain Text
项目
产品
储值
次卡
时效卡
```

---

# CAR\-021 套餐售出后内容不可替换

管理员修改套餐配置：

> 只影响未来销售。
> 
> 

历史套餐继续按照销售时内容执行。

---

# CAR\-022 套餐支持跨店使用

直营门店之间无需转卡。

---

# CAR\-023 套餐支持延期

延期需要：

```Plain Text
权限
原因
原有效期
新有效期
操作记录
```

---

# CAR\-024 套餐内项目允许单独退款

例如：

```Plain Text
套餐：
项目A
项目B
产品C
```

客户可以：

> 只退项目A。
> 
> 

不能要求整个套餐一起退款。

---

# CAR\-025 套餐退款必须按销售时的退款价值计算

禁止直接使用当前项目价格：

```Plain Text
当前项目售价 × 数量
```

因为未来项目价格可能发生变化。

必须：

> 在套餐销售时就保存该权益项的退款/折现金额。
> 
> 

---

# CAR\-026 套餐项目可折现为会员账户现金

你已经确定：

> 套餐项目可以退款后变成账户内现金。
> 
> 

因此这不是简单的“现金支付退款”。

而是：

```Plain Text
套餐权益减少
+
会员账户现金增加
```

具体账户归属需要与现有旧系统口径保持一致。

---

# CAR\-027 套餐退款必须检查已经使用的权益

例如：

```Plain Text
项目A总10次
已使用3次
```

最多只能处理：

```Plain Text
剩余7次
```

是否允许针对已使用部分做特殊退款，由REF规则决定。

---

# 八、通用次卡规则

# CAR\-040 次卡支持跨店使用

直营体系下不需要门店间转卡。

---

# CAR\-041 次卡支持延期

必须记录：

```Plain Text
原有效期
新有效期
延期原因
操作人
```

---

# CAR\-042 次卡支持客户之间转让

注意：

> 这里是客户与客户之间转让。
> 
> 

不是门店之间转让。

---

# CAR\-043 次卡转让必须经过审批

流程：

```Plain Text
申请
 ↓
审批
 ↓
执行
```

普通员工不能直接修改持有人。

---

# CAR\-044 次卡转让前必须进行业务检查

至少检查：

```Plain Text
卡是否有效
是否已经过期
是否被冻结
是否存在退款
是否存在未完成业务
```

---

# CAR\-045 次卡消费次数必须按业务明细记录

即使“一次消费次数不限”，系统也必须记录：

```Plain Text
本次消耗数量
```

避免未来无法统计。

---

# CAR\-046 次卡退款恢复规则暂定

目前你尚未最终确定。

暂时定义为：

> **系统必须支持权益恢复，但最终恢复数量和退款计算方式在05业务规则最终确认时锁定。**
> 
> 

开发阶段不能自行决定。

---

# 九、时效卡规则

# CAR\-060 时效卡以有效期\+周期规则控制

系统必须判断：

```Plain Text
当前日期
有效期
当前周期
周期额度
已用额度
```

---

# CAR\-061 时效卡不能仅按“总次数”判断

例如：

```Plain Text
每7天3次
```

必须知道当前周期是否已经用满。

---

# CAR\-062 时效卡延期按照延期规则处理

不直接覆盖历史有效期数据而无记录。

---

# 十、销售规则

# SAL\-001 销售代表客户购买行为

销售范围包括：

```Plain Text
项目
产品
储值卡
套餐卡
通用次卡
时效卡
```

---

# SAL\-002 销售订单与支付订单分离

销售订单负责：

> 客户购买了什么。
> 
> 

支付负责：

> 客户实际怎么支付。
> 
> 

---

# SAL\-003 一个销售订单可以多个明细

例如：

```Plain Text
项目
+
产品
+
储值卡
```

---

# SAL\-004 一个销售订单允许多种支付方式

例如：

```Plain Text
微信
+
现金
+
储值
```

---

# SAL\-005 未支付订单可以取消

未支付：

```Plain Text
取消 → 关闭
```

一般不会产生退款。

---

# SAL\-006 已支付订单不能直接删除

必须进入：

```Plain Text
退款/冲销
```

---

# SAL\-007 销售订单修改权限按状态控制

例如：

```Plain Text
草稿：
可以修改

待支付：
有限修改

已支付：
禁止普通员工修改
```

具体以旧系统现有行为最终核对。

---

# SAL\-008 成交价格必须可追溯

订单必须知道：

```Plain Text
原价
折扣
优惠
实际成交
改价员工
```

---

# 十一、支付规则

# PAY\-001 支付成功必须有唯一支付记录

不能同一支付业务创建两条成功记录。

---

# PAY\-002 支付接口必须幂等

尤其：

```Plain Text
微信
支付宝
充值
订单支付
退款
```

---

# PAY\-003 第三方支付异常必须支持主动查询

不能要求客户再次付款解决系统超时。

---

# PAY\-004 会员权益支付不等于现金支付

例如：

```Plain Text
储值本金300
```

属于：

> 使用会员已有资产。
> 
> 

不是：

> 今天新增收款300。
> 
> 

---

# PAY\-005 实收与消耗金额不能混淆

例如：

```Plain Text
耗卡300
```

可能：

```Plain Text
实收 = 0
消耗 = 300
```

---

# 十二、消耗/耗卡规则

这是第二核心规则域。

# TRT\-001 消耗代表会员使用已有权益

会员到店后：

> 不是重新购买，而是兑现以前销售形成的会员权益。
> 
> 

---

# TRT\-002 耗卡必须绑定客户

不能脱离客户直接创建正常耗卡。

---

# TRT\-003 每次耗卡必须选择具体项目/产品/服务

不能只记录：

```Plain Text
客户耗卡300
```

而不知道耗的是什么。

---

# TRT\-004 每次耗卡必须知道权益来源

例如：

```Plain Text
储值本金
储值赠金
套餐
通用次卡
时效卡
```

---

# TRT\-005 护理师可以自主选择储值抵扣来源

例如：

```Plain Text
本金
赠金
混合
```

由操作时选择。

---

# TRT\-006 跨店耗卡必须重新校验权益使用范围

不能因为客户拥有权益就直接允许。

必须判断：

```Plain Text
当前门店
权益类型
权益来源门店
跨店规则
```

---

# TRT\-007 耗卡必须校验有效期

过期权益：

> 默认不可直接使用。
> 
> 

除非已经走延期。

---

# TRT\-008 耗卡完成后形成消耗金额

例如：

```Plain Text
项目300
```

即使没有新增支付：

```Plain Text
消耗金额 = 300
```

---

# TRT\-009 消耗金额不等于销售金额

例如：

```Plain Text
客户本月没有办卡
但是耗卡5000
```

则：

```Plain Text
销售 = 0
消耗 = 5000
```

---

# TRT\-010 一次服务可以有多个护理师

必须支持：

```Plain Text
张三60%
李四40%
```

---

# TRT\-011 护理师分配比例总和必须100%

例如：

```Plain Text
60% + 40% = 100%
```

否则不能提交。

---

# TRT\-012 消耗完成必须具有唯一性

同一业务不能重复完成两次。

---

# TRT\-013 并发耗卡必须防止超扣

例如只剩1次：

```Plain Text
A操作成功
B必须失败
```

不能出现负次数。

---

# 十三、服务规则

# SRV\-001 服务完成才形成正式服务客流

不能因为：

```Plain Text
开单
付款
```

就直接计一个服务客流。

---

# SRV\-002 服务人员与销售人员可以不同

例如：

```Plain Text
销售：张三
护理：李四
```

允许。

---

# SRV\-003 服务人员可以多人

支持比例：

```Plain Text
A 70%
B 30%
```

---

# SRV\-004 服务人员分配应在业务发生时确定

原则上：

> 不由月底财务人员重新猜测。
> 
> 

---

# SRV\-005 服务客流与消耗金额独立

例如：

```Plain Text
消耗300
服务客流1
```

两个指标分别统计。

---

# SRV\-006 赠送体验可以产生服务客流

例如：

```Plain Text
销售 = 0
消耗 = 0
服务客流 = 1
```

是否产生其他绩效，要看具体绩效方案。

---

# 十四、业绩规则

这是你们项目最需要重点控制的一章。

---

# PER\-001 至少存在三类核心经营指标

```Plain Text
销售业绩
消耗业绩
服务客流
```

---

# PER\-002 销售业绩来源于销售业务

例如：

```Plain Text
办卡
项目销售
产品销售
```

形成销售业绩。

---

# PER\-003 消耗业绩来源于耗卡业务

例如：

```Plain Text
会员耗卡300
```

根据规则产生：

> 消耗业绩。
> 
>

# PER\-004 服务客流来源于服务完成

服务完成：

```Plain Text
Guest = 1
```

# PER\-005 销售和耗卡业绩必须分开累计

```Plain Text

```

必须分别记录。

不能合成：

```Plain Text
总业绩150000
```

然后丢失原始维度。

# PER\-006 员工多人服务时，业绩按照服务分配比例拆分


```Plain Text

```

# PER\-007 业绩的“业务事实”和“提成金额”必须分开

```Plain Text

```

不等于：

```Plain Text
提成9
```

```Plain Text
300
```

提成结果：

```Plain Text
9
```

两层数据不能混。

# PER\-008 实际业绩与系统业绩可以存在不同口径

根据当前业务说明，系统至少需要预留：

```Plain Text

系统业绩
```

其中：

> **赠金不计入实际业绩。**
> 
> 

最终两套口径具体计算仍需与原系统规则逐项核对。

# PER\-009 卡权益抵扣不能默认等同销售业绩

# 十六、客流规则——这里需要一个正式定义

这是目前业务中仍值得进一步确认的一项。

建议V1默认：

> **一次完整服务对应1个服务客流。**
> 
> 

例如一个客户由：

```Plain Text
张三60%
李四40%
```

服务。

系统内部可以记录：

```Plain Text
总客流 = 1
```

然后再根据客流分摊规则：

```Plain Text
张三 = 0.6客
李四 = 0.4客
```

这样：

```Plain Text
张三 + 李四 = 1客
```

避免一位客户被统计成两客。

但如果你们旧系统的逻辑实际上是：

> **参与服务的每个人都各算1客流**
> 
> 

那么这里必须以旧系统为准。

这项建议在后续核对旧系统业务时作为重点确认项。

# 三十二、业务规则设计原则

### 第二：

> 
> 

### 第三：

> 
> 

### 第四：

> 
> 

### 第五：

> 如果撤销/退款，会怎么反向处理？
> 
> 

这五个问题就是你以后带开发团队最重要的思维方式。
