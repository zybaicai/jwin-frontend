**项目名称：** 养发直营连锁ERP自主研发项目

---

# 一、领域模型设计目标

1. 系统有哪些业务领域；

2. 每个领域有哪些核心业务对象；

3. 业务对象之间是什么关系；

4. 一个业务对象由谁创建；

5. 一个业务对象会影响哪些其他业务对象；

6. 未来程序代码应该按照什么业务边界组织。

---

# 二、领域建模总原则

## 2\.1 领域模型不等于数据库表

旧系统已经运行多年，数据库中存在大量针对不同业务类型拆开的表。

例如销售体系存在：

```Plain Text
TB_SaleBill
TB_SaleBillProject
TB_SaleBillProduct
TB_SaleBillSavingCard
TB_SaleBillPackageCard
TB_SaleBillGeneralCard
TB_SaleBillTimeCard
```

领域层不应该因为有这些表就创建：

```Plain Text
SaleBillProjectDomain
SaleBillProductDomain
SaleBillSavingCardDomain
...
```

而应该抽象为：

```Plain Text
销售订单
    ↓
销售订单明细
        ├── 项目
        ├── 产品
        ├── 储值卡
        ├── 套餐卡
        ├── 通用次卡
        └── 时效卡
```

# 五、01组织与权限域

## 5\.1 领域目标

解决：

> 谁属于哪个组织/门店、是什么身份、可以做什么、可以查看什么、可以在哪个门店操作。
> 
> 

---

# 5\.2 核心领域对象

```Plain Text
Organization
Store
Employee
JobType
Role
Permission
EmployeeStoreRelation
EmployeeRoleRelation
```

---

# 5\.3 Organization

## 业务含义

公司/集团/直营组织主体。

例如：

```Plain Text
总部
```

一个 Organization 下可有多个直营门店。

关系：

```Plain Text
Organization
    │
    ├── Store A
    ├── Store B
    ├── Store C
    └── Store D
```

---

# 5\.4 Store

## 业务含义

业务实际发生的经营单位。

门店是大量业务的业务上下文：

```Plain Text
销售发生在哪个门店
消耗发生在哪个门店
库存属于哪个门店
员工在哪个门店
客户在哪个门店服务
业绩归属哪个门店
```

所以后续绝大部分交易对象必须能够追溯 Store。

---

# 5\.5 Employee

## 业务含义

系统中的实际业务人员。

注意：

> Employee 不等于 LoginUser。
> 
> 

Employee代表真实员工。

可能承担：

```Plain Text
销售人员
顾问
护理师
服务人员
收银员
店长
运营
财务
渠道人员
```

一个员工可以拥有多个角色，也可能跨多个门店。

---

# 5\.6 JobType

职位/岗位。

例如：

```Plain Text
店长
顾问
护理师
前台
财务
运营
```

职位本身不等于系统权限，但会参与：

- 角色分配；

- 绩效规则；

- 提成方案；

- 数据范围。

---

# 5\.7 EmployeeStoreRelation

员工与门店关系。

例如：

```Plain Text
员工A
 ├── 杭州A店：主门店
 └── 杭州B店：兼职/跨店
```

或者：

```Plain Text
2026-01 ~ 2026-06
杭州A店

2026-07 ~ 至今
杭州B店
```

因此不能简单覆盖员工历史门店。

---

# 5\.8 Role

角色。

例如：

```Plain Text
总部管理员
总部运营
总部财务
区域负责人
店长
前台
顾问
护理师
库管
```

---

# 5\.9 Permission

权限最少分四层：

```Plain Text
菜单权限
页面权限
按钮权限
数据范围权限
```

例如退款：

```Plain Text
查看退款
发起退款
审批退款
执行退款
```

必须是不同权限。

# 六、02客户与会员域

这是系统第二核心领域。

---

# 6\.1 Customer

## 业务含义

真实客户主体。

Customer解决：

> “这个人是谁？”
> 
> 

例如：

```Plain Text
张三
手机号138xxxx
性别男
来源：美团
```

---

# 6\.2 为什么 Customer 和会员权益要分开

新客：

```Plain Text
Customer
```

就已经存在。

当客户办卡以后：

```Plain Text
Customer
    ↓
Membership / Entitlement
```

而不是：

```Plain Text
Customer → 直接变成另一张会员表
```

---

# 6\.3 CustomerProfile

客户基础资料。

包括：

```Plain Text
姓名
手机号
性别
生日
地址
头像
来源
渠道
备注
基础档案
文件档案
```

---

# 6\.4 CustomerStoreRelation

客户与门店关系。

直营体系的关键规则：

> **会员权益跨直营门店通用，不需要门店之间转卡。**
> 
> 

因此：

```Plain Text
Customer
   ├── A店关系
   ├── B店关系
   └── C店关系
```

可以记录：

```Plain Text
首次到店
最近到店
归属门店
维护门店
消费门店
```

---

# 6\.5 CustomerLevel

会员等级。

例如：

```Plain Text
普通会员
银卡会员
金卡会员
钻石会员
```

对应功能清单：

```Plain Text
入会门槛
等级设置
成长值任务
升降级规则
```

---

# 6\.6 CustomerTag

客户标签。

例如：

```Plain Text
新客
高价值
沉睡
高频
重点维护
敏感客户
```

---

# 6\.7 CustomerServicer

客户服务人员/归属人员。

用于记录：

> 谁主要负责这个客户。
> 
> 

它和“本次服务员工”不是同一个概念。

例如：

```Plain Text
客户归属顾问：张三
本次护理师：李四
```

必须分开。

---

# 6\.8 DiagnosisRecord

接诊/诊断记录。

解决：

> 客户本次到店前后，有什么需求、问题、建议、诊断结果。
> 
> 

后续可以成为：

```Plain Text
客户画像
服务历史
复购分析
回访依据
```

# 7\.1 Product

代表实物商品。

例如：

```Plain Text

精华
家庭产品

```

产品可能参与：

```Plain Text
销售
库存
退款
赠送
项目耗材
```

---

# 7\.2 Project

代表服务项目。

例如：

```Plain Text

头疗
护理

```

```Plain Text

```

---

# 7\.3 ProjectConsumableTemplate

这是养发ERP特别重要的领域对象。

表示：

> 一个服务项目完成时，会消耗哪些物料。
> 
> 

例如：

```Plain Text

产品X 10ml
产品Y 5ml
```

关系：

```Plain Text

   ↓
ConsumableTemplate

```

---

# 7\.4 PriceRule

用于支持：

```Plain Text

会员价
指定门店价格

```

# 八、04会员权益域

这是整个ERP最特殊的核心领域。

这里不应该只是叫“卡管理”。

真正的业务意义是：

# 会员资产/权益管理

客户购买以后，系统生成的是：

> 会员可使用的资产。
> 
> 

---

# 8\.1 四类核心权益

```Plain Text
SavingCard
PackageCard
GeneralCard
TimeCard
```

即：

```Plain Text
储值卡
套餐卡
通用次卡
时效卡
```

---

# 8\.2 权益定义和会员账户必须分开

例如：

```Plain Text
“黄金养发卡”
```

是一个权益商品定义。

而：

```Plain Text
“张三持有黄金养发卡”
```

是一个会员账户实例。

所以：

```Plain Text
SavingCardDefinition
        ↓
SavingCardAccount
```

---

# 8\.3 SavingCard

储值卡产品定义。

包含：

```Plain Text
卡名称
售价
本金
赠金
有效期
销售门店
使用范围
```

---

# 8\.4 SavingCardAccount

某位客户实际拥有的储值账户。

核心资产：

```Plain Text
本金余额
赠金余额
有效期
来源销售单
来源门店
当前状态
```

业务规则：

```Plain Text
本金：
允许跨店

赠金：
不允许跨店

默认：
3年有效期
```

---

# 8\.5 SavingCardTransaction

储值账户流水。

所有变化都来自：

```Plain Text
充值
消耗
退款
延期
人工调整
冲正
```

例如：

```Plain Text
充值 +10000本金
充值 +2000赠金

消耗 -300本金

退款 +200本金
```

---

# 8\.6 套餐卡

PackageCard是一种：

> **组合权益容器。**
> 
> 

例如：

```Plain Text
套餐A
│
├── 项目A × 10
├── 产品B × 2
├── 储值500
└── 时效卡1张
```

旧系统存在：

```Plain Text
TB_PackageCardProject
TB_PackageCardProduct
TB_PackageCardSavingCard
TB_PackageCardGeneralCard
TB_PackageCardTimeCard
```

这与该领域模型完全对应。

---

# 8\.7 PackageCardAccount

代表：

> 某个客户实际购买的一份套餐。
> 
> 

不能只保存一个“套餐余额”。

而应该能追踪：

```Plain Text
套餐整体
 ↓
套餐权益项
 ↓
每个权益项
总量
已用
剩余
可退
```

---

# 8\.8 GeneralCard

通用次卡。

代表：

> 以次数作为核心权益的会员资产。
> 
> 

例如：

```Plain Text
养发10次
```

生命周期：

```Plain Text
购买10次
 ↓
剩余10
 ↓
消耗1
 ↓
剩余9
```

支持：

```Plain Text
跨店
延期
客户转让
审批
```

---

# 8\.9 TimeCard

时效卡。

核心是：

```Plain Text
有效期
周期
周期次数
已使用
剩余次数
```

不是简单的总次数卡。

# 九、05销售交易域

这是ERP第一核心交易领域。

---

# 9\.1 Sales

定义：

> 客户实际购买商品、项目或会员权益的业务行为。
> 
> 

---

# 9\.2 SaleOrder / SaleBill

代表：

> 一次销售行为。
> 
> 

例如：

```Plain Text
张三
杭州A店
2026-08-26

黄金储值卡10000
养护产品300
```

是一张销售订单。

---

# 9\.3 SaleOrderItem

一张销售订单里面可以有：

```Plain Text
项目
产品
储值卡
套餐卡

```

所以领域统一抽象为：

```Plain Text

   ↓
SaleOrderItem
```

由 `itemType` 区分。

# 9\.4 SaleHandler

销售经手人。

一个销售订单可能有：

```Plain Text
主销售人员
辅助销售人员
顾问
渠道人员
```

后面提成计算会使用这些人员关系。

---

# 9\.5 Sales Business State

销售订单至少包含：

```Plain Text
草稿
待支付
部分支付
已支付
已完成
已关闭
部分退款
已退款
```

具体状态如何映射旧系统，在04《核心业务流程》中正式确定。

# 十、06支付结算域

Payment解决：

> 客户到底实际怎么付款。
> 
> 

---

# 10\.1 Payment

支付是销售的组成结果，但不是销售本身。

例如：

```Plain Text
销售订单5000
```

支付：

```Plain Text
微信2000
现金1000
储值2000
```

因此：

```Plain Text
SaleOrder
   ↓
Payment*
```

---

# 10\.2 PaymentType

至少包括：

```Plain Text
现金
微信
支付宝
银行卡
储值本金
储值赠金
其他
```

旧系统具体付款方式继续兼容。

---

# 10\.3 Payment与会员权益

这里必须区分：

```Plain Text
真正支付
```

与：

```Plain Text
使用既有会员权益
```

例如：

客户今天耗卡300：

```Plain Text
新的现金支付 = 0
会员权益减少 = 300
消耗额 = 300
```

所以：

> **消耗不是支付。**
> 
> 

这是以后所有代码设计必须遵守的原则。

---

# 十一、07消耗/耗卡域

这是ERP第二核心交易领域。

---

# 11\.1 TreatOrder / TreatBill

业务定义：

> 客户本次实际使用以前购买的权益，并完成服务的业务事实。
> 
> 

例如：

```Plain Text
张三到店

选择：
养发项目300

使用：
储值本金

护理师：
王五60%
李四40%
```

这是一笔消耗业务。

---

# 11\.2 TreatOrderItem

消耗明细。

可能消耗：

```Plain Text
项目
产品
储值
套餐项目
通用次卡
时效卡
```

---

# 11\.3 TreatSource

每一笔消耗必须知道：

> 从哪个会员权益中扣。
> 
> 

例如：

```Plain Text
SAVING_PRINCIPAL
SAVING_BONUS
PACKAGE
GENERAL_CARD
TIME_CARD
```

---

# 11\.4 消耗的业务结果

完成一次消耗后，理论上可能同时形成：

```Plain Text
会员权益扣减
+
消耗金额
+
服务客流
+
消耗业绩
+
库存消耗
```

但这几个结果不是同一个对象。

---

# 十二、08服务履约域

这个领域解决：

> 客户实际有没有接受服务，以及谁提供了服务。
> 
> 

---

# 12\.1 ServiceRecord

服务记录。

例如：

```Plain Text
客户张三
养发
2026-08-26
服务开始10:00
服务结束11:20
```

---

# 12\.2 ServiceEmployeeAllocation

服务人员分配。

根据你明确的业务规则：

> 护理师开单/耗卡时手动选择服务员工并分配比例。
> 
> 

例如：

```Plain Text
王五 60%
李四 40%
```

因此一个服务可以有多个服务人员。

---

# 12\.3 ServiceGuest

服务客流。

定义：

> 一个实际发生服务的客户事实。
> 
> 

例如：

```Plain Text
客户张三
服务完成
→
产生1个服务客流
```

如果未来允许多人共享客流，再配置权重。

---

# 12\.4 ServiceGuest与消耗金额必须分开

例如：

```Plain Text
消耗金额 = 300
服务客流 = 1
```

这是两个业务指标。

后面员工提成完全可能：

```Plain Text
消耗提成：
300 × X%

客流提成：
1 × 8元
```

---

# 十三、09库存供应链域

---

# 13\.1 Inventory

当前库存状态。

---

# 13\.2 InventoryTransaction

库存变化事实。

任何库存变化都需要能够追溯来源。

例如：

```Plain Text
采购入库
产品销售
项目耗材
调拨
盘点
退款
手工调整
```

---

# 13\.3 产品销售 vs 项目耗材

必须分开。

### 产品销售：

```Plain Text
客户购买产品
 ↓
销售
 ↓
库存减少
```

### 项目耗材：

```Plain Text
客户服务
 ↓
项目完成
 ↓
按照耗材规则
 ↓
库存减少
```

# 三十七、下一章03的输入

03《功能模块设计》不能重新从空白开始。

它必须直接基于：

```Plain Text
01 产品总体架构
        ↓
02 领域模型
        ↓
03 功能模块
```

并把你现有功能清单里的约210个功能点全部落下来。

03最终建议形成这样的层级：

```Plain Text
一级模块
    ↓
二级模块
    ↓
三级功能
    ↓
具体功能点
    ↓
功能说明
    ↓
操作者
    ↓
业务领域
    ↓
核心对象
    ↓
旧系统对应功能
    ↓
优先级
    ↓
V1.0 / V1.1 / V2.0
```

例如：

```Plain Text
店务管理
└── 开单收银
    └── 开单
        ├── 搜索客户
        ├── 新增客户
        ├── 添加项目
        ├── 添加产品
        ├── 添加储值卡
        ├── 添加套餐卡
        ├── 添加次卡

        ├── 选择销售经手人
        ├── 设置折扣
        ├── 挂单
        └── 收银
```
