# 一、核心业务流程设计原则

## 1\. 销售和消耗永远是两条业务线

整个系统最重要的原则：

```Plain Text
销售：
客户购买了什么

消耗：
客户今天实际使用了什么
```

例如：

```Plain Text
7月1日：
客户办卡10000

7月10日：
客户耗卡300
```

系统应该记录：

```Plain Text
7月1日：
销售 = 10000
实收 = 10000
会员权益 +10000

7月10日：
销售 = 0
消耗 = 300
会员权益 -300
```

两天之间存在关联，但不是同一笔交易。

# 4\.2 新客体验流程

这是你们业务非常重要的一条主流程。

## 场景

客户从美团购买体验项目。

例如：

```Plain Text
体验项目：398元
```

---

## 主流程

```Plain Text
客户到店
 ↓
查询/创建客户
 ↓
选择体验项目
 ↓
创建销售订单
 ↓
选择销售经手人
 ↓
确认价格
 ↓
支付398
 ↓
销售完成
 ↓
创建/记录服务
 ↓
开始体验
 ↓
服务完成
 ↓
产生消耗记录398
 ↓
产生服务客流1
 ↓
形成消耗业绩
 ↓
形成销售业绩
```

---

## 为什么这里同时存在“销售”和“消耗”

因为：

```Plain Text
客户购买了398元体验项目
```

属于：

> 销售事实。
> 
> 

而：

```Plain Text
客户实际接受398元服务
```

属于：

> 消耗/服务事实。
> 
> 

所以：

```Plain Text
销售金额 = 398
消耗金额 = 398
```

两个指标都可能成立。

---

## 特别注意

后续老会员：

```Plain Text
耗卡300
```

没有新的支付。

则：

```Plain Text
销售 = 0
消耗 = 300
```

这是两种完全不同的场景。

# 5\.6 支付成功判断


```Plain Text

```

```Plain Text

```

是否允许“欠款”由旧系统业务规则决定。

# 5\.3 储值卡退款

如果客户从未使用：

```Plain Text
储值本金10000
赠金2000
```

申请退款。

必须先判断：

```Plain Text
本金是否已经使用？
赠金是否已经使用？
是否允许退款？
```

根据你已经确定的规则：

> 赠金本身不能退款。
> 
> 

所以退款逻辑不能简单：

```Plain Text
账户余额 × 某个比例
```

而必须拆本金、赠金分别计算。

# 5\.4 套餐内容不能替换

套餐售出后：

```Plain Text
套餐A
项目A ×10
产品B ×2
储值500
```

即使总部后来把：

```Plain Text
项目A
```

修改成：

```Plain Text
项目C
```

历史已售套餐不能跟着变化。

所以必须保存：

> 销售时的套餐内容快照。
> 
>
