# ERP系统前端 Cursor 开发总规则

> 版本：V1.0
> 适用范围：ERP系统前端全部开发工作
> 技术栈：Vue 3 + TypeScript + Vite + Element Plus + Pinia + Vue Router + Axios
> 开发工具：Cursor
> 后端：Spring Boot
> 文档体系：ERP项目设计文档 V1.0

---

# 一、文档目的

本文件是 ERP 系统前端开发的最高级 Cursor 开发规则。

后续所有前端开发工作，包括：

- 项目初始化
- 登录
- 当前用户
- 权限
- 门店切换
- 系统布局
- 菜单
- 路由
- 客户管理
- 销售开单
- 消耗服务
- 预约中心
- 产品项目
- 卡项
- 绩效
- 库存
- 营销
- 报表
- 系统管理

均必须遵守本文件。

Cursor 不允许脱离项目设计文档，自行设计一套新的业务体系。

---

# 二、Cursor的角色定位

Cursor 在本项目中的角色：

> **高级 Vue 前端开发工程师 + 前端架构工程师。**

Cursor 的主要职责：

1. 根据项目设计文档理解需求。
2. 根据后端 API 实现前端页面。
3. 建立合理的前端工程结构。
4. 编写 Vue / TypeScript / CSS 代码。
5. 完成 API 联调。
6. 实现权限控制。
7. 实现状态管理。
8. 实现统一错误处理。
9. 编写必要的组件。
10. 编写前端测试。
11. 进行代码审查。
12. 修复明确的问题。

Cursor **不是产品经理**。

Cursor **不是业务规则制定者**。

Cursor **不能自行改变 ERP 的业务规则**。

Cursor **不能自行修改后端 API 契约**。

Cursor **不能自行修改数据库设计**。

---



# 三、项目开发总原则

整个前端必须遵循：

> **先基础框架，再业务模块。**

不得一开始直接开发：

- 销售开单
- 客户管理
- 消耗
- 预约
- 卡项
- 绩效

必须先建立完整的前端基础平台。

---



# 四、前端整体建设顺序

前端必须按照以下顺序开发。

## 第一阶段：项目初始化

建立：

- Vue 3
- TypeScript
- Vite
- Element Plus
- Pinia
- Vue Router
- Axios

这一阶段只解决：

> “前端项目能正常运行。”

不得在这一阶段开发业务功能。

---



# 五、第二阶段：前端基础框架

第二阶段建立 ERP 前端基础平台。

必须包含：

### 1. 登录

包括：

- 登录页面
- 用户名/账号
- 密码
- 登录接口
- Token 保存
- 登录成功跳转
- 登录失败提示
- 登录状态恢复

---



### 2. 当前用户

建立：

- 当前用户 Store
- 用户基本信息
- 员工信息
- 角色信息
- 权限编码
- 数据权限
- 可用门店

当前用户信息原则上通过：

```text
GET /api/v1/auth/me
```

获取。

不得在前端硬编码当前用户。

---



### 3. Token

建立统一 Token 管理。

包括：

- Token 保存
- Token 获取
- Token 清除
- Axios 自动携带 Token
- 登录失效处理

Axios 请求必须自动携带认证信息。

---



### 4. 401处理

当后端返回：

```text
401 Unauthorized
```

必须：

1. 清除本地登录状态。
2. 清除 Token。
3. 清除用户状态。
4. 跳转登录页面。
5. 避免重复跳转。
6. 给用户合理提示。

不得让页面停留在一个已经失效的登录状态。

---



### 5. 403处理

当后端返回：

```text
403 Forbidden
```

必须统一处理。

原则：

> 当前用户没有执行该操作的权限。

前端应显示明确的无权限提示。

不能把 403 当成普通 500 错误处理。

---



# 六、第三阶段：ERP主框架

登录完成之后进入 ERP 主框架。

必须建立：

```text
App
 └── MainLayout
      ├── Sidebar
      ├── Header
      ├── Breadcrumb
      └── MainContent
```

---



## Sidebar

左侧菜单必须支持：

- 一级菜单
- 二级菜单
- 菜单图标
- 菜单展开
- 菜单折叠
- 当前菜单高亮
- 权限过滤

不能直接把所有菜单写死给所有用户。

---



## Header

顶部至少包含：

- 当前门店
- 当前用户
- 用户头像
- 用户名称
- 用户菜单
- 退出登录

后续可以扩展：

- 消息
- 待办
- 全屏
- 系统设置

---



## Breadcrumb

根据当前路由自动生成面包屑。

例如：

```text
首页 / 客户管理 / 客户列表
```

不得在每个页面手工重复维护。

---



# 七、第四阶段：门店上下文

ERP 是直营连锁门店系统。

因此：

> **当前门店是整个前端系统非常重要的上下文。**

必须建立：

```text
CurrentStore
```

概念。

至少包括：

```text
storeId
storeName
```

以及后续后端返回的其他门店信息。

---



# 八、门店切换规则

门店切换不能简单理解为：

```typescript
currentStoreId = xxx
```

门店切换必须是一个完整动作。

流程：

```text
用户点击门店
      ↓
判断用户是否拥有该门店权限
      ↓
切换当前门店
      ↓
更新当前门店状态
      ↓
清理门店相关缓存
      ↓
刷新需要依赖门店的数据
      ↓
重新加载当前页面
```

---



# 九、门店权限原则

用户只能切换到自己允许访问的门店。

例如：

```text
用户可访问门店：
├── 杭州黄龙店
├── 杭州乐堤港店
└── 宁波环球银泰店
```

则前端只能显示这些门店。

不能让用户输入任意：

```text
storeId
```

然后切换过去。

---



# 十、门店切换后的数据处理

以下数据通常属于门店上下文：

- 当前员工
- 项目
- 门店价格
- 门店库存
- 门店客户
- 门店预约
- 门店排班
- 门店业绩
- 门店订单
- 门店报表

因此切换门店以后：

> 不能继续使用旧门店缓存的数据。

必须根据页面实际情况：

- 清理缓存
- 重新请求
- 刷新页面状态

---



# 十一、权限模型

前端权限必须至少区分三层：

```text
菜单权限
路由权限
按钮/操作权限
```

---



## 11.1 菜单权限

控制：

> 用户能不能看到这个菜单。

例如：

```text
客户管理
销售管理
预约中心
库存管理
报表中心
系统管理
```

没有权限则不显示。

---



## 11.2 路由权限

控制：

> 用户能不能直接访问这个页面。

即使用户手动输入：

```text
/sales/order
```

如果没有权限，也不能进入。

---



## 11.3 按钮权限

控制：

> 用户能不能执行具体操作。

例如：

```text
新增客户
修改客户
删除客户
开单
改价
退款
审核
导出
```

按钮是否显示或是否可用，需要根据权限控制。

---



# 十二、前端权限不是最终安全边界

必须明确：

> **前端权限控制不能替代后端权限控制。**

前端权限主要用于：

- 菜单隐藏
- 页面拦截
- 按钮隐藏
- 用户体验

真正的安全校验必须由后端完成。

例如：

```text
前端隐藏“改价”
```

并不意味着：

```text
后端允许所有人修改价格。
```

后端仍然必须校验权限。

---



# 十三、后端API原则

前端必须：

> **以实际后端 API 为准。**

项目已有后端 API 文档和后端代码。

Cursor 开发页面之前，必须先检查：

1. API 文档。
2. API Controller。
3. DTO。
4. Response。
5. 参数结构。
6. 枚举。
7. 权限编码。
8. 当前项目已有 API 封装。

不得自己假设接口。

---



# 十四、禁止自行创造API

例如后端没有：

```text
GET /api/v1/customer/list
```

Cursor 不得因为前端方便就自行使用这个接口。

必须先确认真实接口。

如果发现：

> 产品设计需要某个接口，但后端目前没有。

必须停止并报告：

```text
发现前端需求与当前后端API存在缺口。

需求：
xxx

当前API：
xxx

缺少：
xxx

建议：
方案A：
方案B：

需要人工确认。
```

不得自行修改后端。

---



# 十五、API请求统一管理

不得在每一个 Vue 页面中重复创建 Axios 实例。

例如禁止：

```typescript
axios.create(...)
```

在各个页面重复出现。

应该建立统一 API 基础层。

例如：

```text
src/
├── api/
│   ├── auth.ts
│   ├── customer.ts
│   ├── sales.ts
│   ├── appointment.ts
│   └── ...
```

统一请求实例：

```text
src/utils/request.ts
```

---



# 十六、Axios拦截器

统一处理：

### 请求拦截

负责：

- Token
- 公共请求头
- 请求配置



### 响应拦截

负责：

- 成功响应
- 业务错误
- 401
- 403
- 500
- 网络错误

页面本身不要重复实现这些逻辑。

---



# 十七、错误处理原则

错误必须分层处理。

## 业务错误

例如：

```text
余额不足
库存不足
客户不存在
卡项已过期
预约时间冲突
```

由页面根据业务场景显示。

---



## 权限错误

```text
401
403
```

统一处理。

---



## 系统错误

例如：

```text
500
网络异常
接口超时
服务不可用
```

统一处理。

---



# 十八、Loading原则

页面请求数据时必须考虑：

```text
loading
```

至少处理：

```text
加载中
加载成功
加载失败
空数据
```

不能出现：

> 页面白屏，用户不知道发生了什么。

---



# 十九、空数据原则

列表页面必须考虑：

```text
暂无数据
```

不能把：

```text
[]
```

直接渲染成空白区域。

应该使用 Element Plus 的：

```text
el-empty
```

或者统一空状态组件。

---



# 二十、防重复提交

以下操作必须重点防止重复提交：

- 登录
- 保存
- 开单
- 支付
- 退款
- 消耗
- 提交预约
- 审核
- 作废

例如：

```text
用户点击支付
↓
按钮立即进入loading
↓
禁止再次点击
↓
等待后端结果
↓
成功/失败后恢复
```

不能让用户连续点击产生重复请求。

---



# 二十一、金额处理原则

ERP 是业务系统。

涉及金额时：

> 前端不得使用 JavaScript 浮点数直接做核心金额计算并作为最终结果提交。

例如不要依赖：

```javascript
0.1 + 0.2
```

得到最终业务金额。

涉及：

- 销售金额
- 实收金额
- 折扣
- 卡项金额
- 退款金额
- 绩效金额
- 佣金金额
- 支付金额

必须以后端计算结果为最终依据。

前端主要负责：

- 展示
- 用户输入
- 基础交互
- 提交参数

---



# 二十二、后端是业务规则最终来源

前端可以做体验层校验。

例如：

```text
金额不能小于0
手机号格式不正确
必填项不能为空
```

但是：

> 业务规则最终必须以后端为准。

例如：

```text
这个员工是否有权限改价
这个卡能不能跨店
这个卡是否过期
这个项目能不能退款
这个员工是否可以操作该门店
这个预约时间是否冲突
```

不能只靠前端判断。

---



# 二十三、页面组件原则

不要把所有代码全部写进一个：

```text
xxx.vue
```

大型页面必须拆分。

例如销售页面后续可能拆成：

```text
SalesOrderPage.vue

components/
├── CustomerSelector.vue
├── ProductSelector.vue
├── SaleItemTable.vue
├── PerformanceAllocation.vue
├── PaymentDialog.vue
└── OrderSuccess.vue
```

组件拆分原则：

> 一个组件负责一个相对明确的职责。

---



# 二十四、组件不要过度拆分

不要为了“组件化”而组件化。

例如：

```text
Button.vue
Input.vue
Label.vue
Text.vue
```

这种没有实际业务价值的重复封装不要随意建立。

优先使用：

```text
Element Plus
```

已有能力。

只有当组件具有：

- 复用价值
- 业务意义
- 明确复杂度

时再抽取。

---



# 二十五、状态管理原则

使用：

```text
Pinia
```

统一管理真正需要跨页面共享的状态。

例如：

```text
用户状态
权限状态
当前门店
系统配置
```

不要把所有页面数据全部放进 Pinia。

页面自己的查询条件、弹窗状态、表格状态，原则上留在页面内部。

---



# 二十六、Router原则

Vue Router 负责：

- 页面路由
- 页面跳转
- 路由权限
- 页面标题
- 面包屑信息
- KeepAlive相关配置

路由配置必须结构清晰。

例如：

```text
/auth
/home
/customer
/sales
/consumption
/appointment
/inventory
/performance
/report
/system
```

具体路径以后以项目设计文档为准。

---



# 二十七、KeepAlive原则

不是所有页面都必须缓存。

适合缓存：

```text
列表页
查询页
工作台
```

例如：

```text
客户列表
订单列表
预约列表
```

需要根据实际体验决定。

不适合盲目缓存：

```text
支付页
新增页面
编辑页面
强状态弹窗页面
```

---



# 二十八、页面生命周期原则

页面需要明确：

```text
进入页面
↓
初始化
↓
加载数据
↓
用户操作
↓
保存
↓
刷新
↓
离开
```

如果页面依赖当前门店：

```text
门店切换
↓
页面重新加载
```

必须保证不会继续显示旧门店数据。

---



# 二十九、代码规范

必须使用：

```text
TypeScript
```

禁止在业务代码中大量使用：

```typescript
any
```

如果必须使用 `any`：

必须说明原因。

优先：

```typescript
interface
type
enum
```

建立清晰的数据类型。

---



# 三十、TypeScript原则

API 返回数据必须有类型定义。

例如：

```typescript
interface CurrentUser {
  id: number
  name: string
  roles: string[]
  permissionCodes: string[]
  storeIds: number[]
}
```

不要大量使用：

```typescript
const data: any
```

---



# 三十一、枚举原则

后端存在明确枚举时：

前端必须尽量建立对应枚举或字典。

例如：

```text
订单状态
支付状态
预约状态
卡类型
消费类型
员工状态
```

不要在页面中大量散落：

```typescript
status === 1
status === 2
status === 3
```

应该统一管理。

---



# 三十二、字典原则

如果系统存在后端字典：

前端应优先使用后端提供的数据。

不要自行维护一套与后端可能不一致的业务字典。

---



# 三十三、表格页面原则

ERP后台大量使用表格。

标准结构优先：

```text
页面标题
↓
查询区域
↓
操作区域
↓
数据表格
↓
分页
```

例如：

```text
客户管理

[姓名] [手机号] [门店] [状态] [查询] [重置]

[新增客户]

------------------------------------------------

客户列表

------------------------------------------------

< 1 2 3 4 5 >
```

---



# 三十四、查询条件原则

列表页面的查询条件必须：

- 有明确字段名称
- 有默认值策略
- 有查询按钮
- 有重置按钮
- 支持回车查询时可考虑回车
- 查询条件与 API 参数明确对应

不要出现：

> 页面有查询条件，但实际没有传给后端。

---



# 三十五、分页原则

分页必须以后端分页接口为准。

前端不要为了方便：

> 一次请求全部数据，然后自己分页。

除非后端明确设计如此。

---



# 三十六、权限按钮原则

按钮权限必须使用统一方式。

例如：

```vue
<el-button
  v-permission="'sales:order:create'"
>
  开单
</el-button>
```

或者统一权限组件。

最终方案必须在基础框架阶段确定。

禁止每个页面自己创造权限判断方式。

---



# 三十七、权限编码原则

权限编码必须以后端返回为准。

例如：

```text
sales:order:create
sales:order:pay
sales:order:refund
sales:order:change-price
```

Cursor 不得自行发明新的权限体系。

如果后端没有明确权限编码：

> 必须先报告。

---



# 三十八、当前用户信息原则

系统登录成功后：

```text
Login
 ↓
Token
 ↓
/auth/me
 ↓
CurrentUserStore
 ↓
权限
 ↓
门店
 ↓
菜单
 ↓
主框架
```

不能只通过登录接口返回的信息直接假设全部权限。

---



# 三十九、退出登录

退出登录必须：

1. 清除 Token。
2. 清除当前用户。
3. 清除权限状态。
4. 清除当前门店。
5. 清除相关缓存。
6. 跳转登录页。

不能只：

```text
router.push('/login')
```

---

# 五十二、性能分配原则

后续销售模块中：

```text

 └── 订单明细
      └── 绩效分配
```

每个项目可以存在多个员工。


前端必须支持产品设计定义的：

```text

```

以及：

```text

```

如果后端最终模型是明细级分配：

> 整单分配只是前端交互方式。

前端必须在提交前转换为后端要求的数据结构。

# 五十三、金额精度原则


必须考虑：

```text

```

尾差问题。

前端展示可以处理交互，但最终金额与比例校验必须以后端为准。

```text
门店
```

为基础。

前端不能自己判断：

可用时间必须以后端返回为准。
