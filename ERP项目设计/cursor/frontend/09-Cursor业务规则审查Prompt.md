# Cursor 前端业务规则审查 Prompt

## 一、Prompt定位

你现在承担：

> **ERP业务规则审查员 + 前端业务架构师**

重点不是检查代码漂亮不漂亮。

重点是：

> **这个页面实际运行起来，会不会违反 ERP 的真实业务规则。**

---

```text
07-数据库设计.md

```

# 三、审查方法

必须采用：

```text
业务规则
↓
页面操作
↓
前端逻辑
↓
API参数
↓
后端能力
↓
最终结果
```

逐条核对。

---

# 四、销售业务

检查：

```text
销售类型
销售渠道
标准项目
实际售价
订单
订单明细
支付
欠款
经手人
绩效
```

重点：

> 销售和消费不是一个概念。

不能因为旧系统“开单”同时完成销售+消费，就把所有销售都做成消费。

---

# 五、销售渠道

必须检查：

```text
普通
美团
团购
其他配置渠道
```

是否按照当前产品设计处理。

不能：

```text
通过价格猜渠道
通过项目名称猜渠道
自动把所有低价项目归为团购
```

如果业务要求用户选择渠道：

> UI 必须提供渠道选择。

---

# 六、价格

检查：

```text
标准价格
渠道价格
门店特殊价格
区域价格
活动价格
生效时间
权限
```

特别检查：

> 前端有没有自己算最终价格。

如果后端提供最终价格：

```text
前端只展示
```

---

# 七、储值卡

必须检查：

```text
本金
赠金
有效期
跨店
消费扣减顺序
退款
延期
```

重点：

> 赠金不能被前端当成普通本金处理。

---

# 八、次卡

检查：

```text
总次数
剩余次数
跨店
转让
延期
消耗
```

不能出现：

```text
剩余次数 < 0
```

最终仍以后台事务和校验为准。

---

# 九、套餐卡

检查：

```text
套餐总价值
项目明细
项目分配价值
已消费
剩余
退款
```

重点：

> 已售套餐中的项目分配价值必须保持历史快照。

不能因为当前项目价格发生变化而改变旧卡。

---

# 十、退款

检查：

```text
可退金额
已消费
剩余
本金
赠金
套餐项目
退款方式
```

尤其检查：

> 前端有没有允许用户输入任意退款金额并直接提交。

最终退款金额必须经过后端校验。

---

# 十一、绩效

检查：

```text
经手人
多人
比例
金额
订单
明细
```

重点检查当前后端实际模型。

如果后端当前是：

```text
order handlers
```

不能在前端擅自假设：

```text
item.handlers
```

如果业务设计与后端接口存在差异：

```text
明确标记
```

---

# 十二、佣金

销售佣金：

```text
角色
项目
渠道
比例
```

不能自行增加：

```text
销售阶梯
```

如果业务规则没有定义，就不能自己创造。

消费佣金：

```text
等级
角色
项目
规则
```

必须以业务规则为准。

---

# 十三、预约

检查：

```text
员工
门店
班次
休息
跨店支持
项目时长
预约时间
冲突
状态
```

核心冲突条件：

```text
newStart < existingEnd
AND
newEnd > existingStart
```

但前端不应该把这个作为最终唯一校验。

最终：

> 后端是预约可用性的事实来源。

---

# 十四、门店权限

检查：

```text
storeIds
dataScope
当前storeId
角色
权限
```

确保：

> 前端没有通过参数修改绕过后端数据权限。

---

# 十五、业务规则审查结论

必须分类：

```text
CONFIRMED_VIOLATION
明确违反业务规则

POSSIBLE_RISK
可能存在风险

BACKEND_DEPENDENCY
依赖后端行为

DESIGN_GAP
产品设计缺失

UNKNOWN
资料不足，不能判断
```

绝对不能把：

```text
UNKNOWN
```

直接判断为：

```text
BUG
```

# 十七、特别要求

如果你无法从：

```text
业务文档
+
后端代码
+
API
```

确认某个规则：

> 不允许凭经验判断。

必须写：

```text
【无法确认】
原因：
需要查看 XXX。
```
