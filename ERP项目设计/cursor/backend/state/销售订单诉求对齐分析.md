## 1. 多护理师 + 手动比例

### 当前已知

- 原型「销售经手人 / 多护理师」：多人勾选，比例合计 100%。  
- 领域：`SaleHandler`；规则 `TRT-011` / `PER-006` 同类约束。  
- 表：`TB_SaleBillHandlerProject|Product|SavingCard|…`（EmployeeID + Scale）。  
- 现码：`CreateSaleOrderCommand.handlers`；`HandlerRatios.assertHundred`。

### 满足方式（无需新表）

开单必填 ≥1 名经手人/护理师（或按货品类型配置的销售经手人角色），每人 `ratio`（百分比），合计 **100±0.01**；写入对应 `TB_SaleBillHandler*`；业绩拆分按 Scale。

### 建议锁定

| 项 | 值 |
|---|---|
| 多人 | 允许 1～N |
| 比例 | 前端可手填；后端强制合计 100% |
| 空比例 | 仅当全体未填时均分；一旦有人填写则全体必须填且合计 100% |
| 业绩 | 归属开单门店业绩事实，再按比例拆到员工 |

**无业务歧义阻断。**

## 2. 补单（本月内往前开业务日）

### 当前已知

- `TB_SaleBill.BillDate`：业务日期；`CreatedOn`：系统录入时间。  
- 设计文档**无**「补单 / 回溯业务日」专条。  
- 现码：`insertSaleBill(..., LocalDateTime.now(), ...)`，不可回溯。

### 【业务歧义】

**问题：** 「本月内前一天」是「仅昨天」，还是「本自然月内任意 ≤ 今天的日期」？

| 方案 | 含义 |
|---|---|
| A | 业务日 ∈ [本月 1 日, 今天]，且 &lt; 今天须有补单权限 |
| B | 仅允许昨天（自然日） |
| C | 可跨月（不推荐，对账混乱） |

**推荐：A**  
**理由：** 对账漏单常见为本月内多日；「前一天」口语多为「往前补」，非「只能昨天」。`CreatedOn` 仍为真实录入时刻，审计不丢。

### 满足方式（无需新表）

- 命令增加可选 `billDate`（日期或日期时间）。  
- 缺省 = 今天（当前门店时区）。  
- 若 `billDate.date < today`：校验 ∈ 本月且 ≤ today，且持有补单权限（建议 `sale:order:backdate`）。  
- `BillDate` = 指定业务日；`CreatedOn` = 服务器当前时间。  
- 报价/活动/特价按 **billDate** 所在时刻解析（活动窗、折扣窗对齐业务日）。

### 建议锁定

采纳 **方案 A** + 补单权限；禁止未来日；禁止跨月。

## 3. 欠尾款（例：1000 储值卡，付 500 欠 500，可用 500）

### 当前已知

- 单头/明细/账户均有 `ArrearAmount`；另有 `*ArrearAmountProcess` 平账表。  
- 《核心业务流程》写「是否允许欠款由旧系统决定」；《业务规则库》「会员账户是否允许欠款/负余额」= **需要确认**。  
- 现码：`updateBillPaid` 把 `ArrearAmount` 置 0；储值开户 `Balance=全额, Arrear=0` —— **不满足**「付 500 用 500」。

### 【业务歧义】

**问题：** 欠款时可用余额如何计算？

| 方案 | 开户口径（储值本金例：面值 1000，实付 500） |
|---|---|
| **A（推荐）** | `Amount/Price` 面值=1000；`Balance`（可用）=**实付本金 500**；`ArrearAmount`=500；后续还款：Arrear↓ Balance↑ |
| B | Balance=1000 全额可用，仅记账欠 500（资金风险大，不推荐） |
| C | 不允许开户至付清（与诉求冲突） |

**推荐：A**  
**理由：** 直接满足「中间过程不影响他的 **500** 余额使用」；旧表字段语义完整；平账过程表可承接还款。

### 连带规则（建议一并锁）

1. 开单允许 `payAmount + arrearAmount = totalAmount`（行/单一致）。  
2. `payAmount > 0` 即可进入「已支付/部分收款」类完成态并**开户**（状态取值复用旧 `BillStatus`，映射时锁定中文值，如保留欠款时仍为可完成态且 `ArrearAmount>0`）。  
3. 可用权益 = 账户 `Balance`/`LargessBalance` 等，**不因 Arrear>0 冻结已入账余额**。  
4. 欠款未清：允许继续耗已入账余额；是否允许再购另议（默认允许）。  
5. 还款（补尾款）可为本模块最小 API，或挂「欠款平账」子能力：写 `*ArrearAmountProcess`，更新账户/单据 Arrear 与 Balance。  
6. 赠金是否随欠款按比例入账：默认 **赠金按实付比例入账或全额入账** —— 见下歧义。

### 【业务歧义】赠金

储值面值本金 1000 + 赠金 200，只付 500 时：

| 方案 | 赠金 |
|---|---|
| G1 | 赠金按实付/本金比例入账（付 50% → 赠金余额 100） |
| G2 | 本金付清前赠金不入账 |
| G3 | 赠金仍全额入账 |

**推荐：G1**（与「付多少用多少」一致）。

### 满足方式

复用 `ArrearAmount` 字段族 + 平账表；**改**开单/支付/开户写入逻辑；不新造「欠款主表」。

## 4. 所属门店 vs 开单门店（跨店销售）

### 当前已知

- **所属门店：** `TB_CustomerEntity` 中 `IsBelongEntity=1` 的 `EntityID`（API：`storeId`/`storeName`）。  
- **注册门店：** 最早建档门店（API 已有 `registerStoreId`）。  
- **开单门店：** `TB_SaleBill.EntityID`；业绩插入用该 `storeId`。  
- 文档：跨店消费不重复建客户主档（CUS-002）。

### 满足方式

| 概念 | 字段 | 规则 |
|---|---|---|
| 顾客所属门店 | `CustomerEntity.IsBelongEntity=1` | A 店顾客到 B 店开单 **不改** 所属 |
| 开单门店 | `SaleBill.EntityID` | = 当前收银门店 B；业绩归 B |
| 账户开户门店 | 账户 `EntityID` | = 开单门店 B（权益开出门店，与旧路径一致） |

VO/详情必须同时返回：

- `customerBelongStoreId` / `customerBelongStoreName`  
- `saleStoreId` / `saleStoreName`（=`EntityID`）

跨店开单：允许 `customerId` 所属 ≠ 当前店；禁止为跨店销售把 `IsBelongEntity` 改到 B。若旧库要求「到店即有 CustomerEntity 行」，可插入 `IsBelongEntity=0` 的 B 店关系行（不抢所属）——与现客户模块「建档绑定」对齐时再落细。

**无阻断；列为 V1 验收项。**
