## 1. 多护理师 + 手动比例

### 已知

- 销售已锁定 **CONF-010**：多人、比例合计 100%、落 Handler、业绩归开单店。  
- 现码 `CreateTreatOrderCommand.handlers` + `HandlerRatios.assertHundred`；**未传则默认当前登录人 100%**。  
- 配置缺失时现码**静默不写** Handler（须改 fail-fast）。

### 满足方式（无新表）

与销售同构：开单必填 ≥1 护理师/经手人，前端定 `ratio`，合计 **100±0.01** → `TB_TreatBillHandler*`。

### 建议锁定（对齐 CONF-010）

| 项 | 值 |
|---|---|
| 多人 | 允许 1～N |
| 比例 | 前端手填；后端强制 100% |
| 缺省 | **不推荐**静默登录人；与销售一致强制选择（或确认保留缺省） |
| 业绩 | 耗卡门店事实 + Handler Scale；员工拆分可与销售同级 V1 |

**无业务歧义阻断（仅确认是否强制必选）。**

## 2. 本月补单（业务日）

### 建议锁定

**直接复用 CONF-011 口径到耗卡**（权限码独立）。

## 3. 选客：全公司可开；跨店搜索须全手机号

### 已知

- CONF-013：所属店 ≠ 开单店允许；不改所属。  
- 现码顾客列表：`TB_CustomerEntity.EntityID = 当前店`，keyword 对姓名/编号/手机 **模糊 LIKE**。  
- 跨店顾客本店可能无 `CustomerEntity` 行。

### 【业务歧义】

| 点 | 选项 |
|---|---|
| 本店搜索 | A：维持模糊（姓名/手机片段）；B：一律全号 |
| 跨店搜索 | **用户要求：必须输入完整手机号**（推荐精确 `=` 全号，禁止 LIKE） |
| 命中后开单 | A：仅 `customerId` 开耗卡，不改所属；必要时插 `IsBelongEntity=0` 的到店关系行；B：禁止无本店关系行的顾客耗卡 |

### 建议锁定

| 项 | 推荐 |
|---|---|
| 接口 | 新增/扩展「耗卡选客」：`scope=STORE|COMPANY`；`COMPANY` 时 **仅当 keyword 为完整手机号** 才查全库 |
| 完整手机号 | 大陆 11 位数字（或配置正则）；不足位数不查跨店 |
| 开单 | 允许跨店客；**不改** `IsBelongEntity`；业绩/TreatBill.EntityID=当前店 |

**须确认：完整号规则 + 无本店关系行是否允许直接开。**

## 4. 项目耗材：可配置；开单自动统计；**不扣库存**

### 已知

- 规则库 **PRO-003 / INV-003**：服务完成后「库存减少」——与用户「**不需要扣掉，只统计**」**冲突**。  
- 实库已有：  
  - `TB_ProjectConsumableTemplate` + `*Product`（产品+最小单位数量）  
  - `TB_ProjectConsumableTemplateProject` / `*ProjectCategory`  
  - 表名含历史换行字符，Mapper 须方括号精确匹配（总规则）  
- **未发现**「耗卡→耗材用量快照且不做出库」的现成流水表；库存域 ERP 扫描为后置。

### 【业务歧义】

| 方案 | 含义 |
|---|---|
| **S（用户口径，推荐写入 CONF）** | 开单成功后按模板展开写入**统计流水**；**不**调用库存出库、不减 `TE_*` 库存余额；门店盘点/对账时只读流水 |
| I（规则库 INV-003） | 同时出库减库存 |

### 满足方式（若锁定 S）

1. **配置**：复用耗材模板表族（项目模块可补 CRUD，或本模块只读）。  
2. **流水**：建议 **C 类新表**（例：`TB_ErpTreatConsumableStat`：TreatBillID、ProjectID、ProductID、Quantity、EntityID、BillDate…）——旧库无对等「只统计」表，不宜硬塞出库单。  
3. 取消/改项目时：同步作废或重算流水（与诉求 6 联动）。

### 建议锁定

采纳用户 **S**；在确认规则中写明 **覆盖 INV-003 对本系统 V1 的适用**（库存实扣留库存中心后续）。  
配置维护入口：本模块只读模板 vs 项目模块维护——建议项目侧配置、耗卡只消费。

**须确认：S vs I；新统计表是否批准（08）。**

## 5. 会员耗卡确认（签字/短信）可配置是否阻断开单

### 已知

- 用户：套餐 / 时效 / 储值 / **次卡** 项目消耗需要确认；可用总部开关控制「阻断开单」或「独立流程」。  
- 实库：`TB_TreatBillSignature(TreatBillID, ImageURL, CreatedOn)` **A 可复用签字图**。  
- **无**「TreatConfirmRequired / 阻断开关」配置表；`TB_MessageConfig` 偏企微推送，**不是**顾客短信验证码开关。  
- 指导书无此开关专条。

### 【业务歧义】

| 点 | 选项 |
|---|---|
| 触发范围 | A：仅卡类账户耗卡（GENERAL/TIME/SAVING/PACKAGE）；B：含普通项目账户 PROJECT |
| 确认渠道 | 签字上传 ImageURL / 短信验证码 / 二者任一 |
| 开关语义 | **Block**：开则未确认单不算成功（权益未扣或已扣待确认？） / **Async**：开单成功，确认独立补录 |
| 阻断时扣卡时机 | B1：确认前不扣权益（挂单） / B2：先扣再确认，失败回滚（复杂） |

### 建议锁定（推荐组合）

| 项 | 推荐 |
|---|---|
| 配置 | **C**：总部开关表（如 `TB_ErpTreatConfirmConfig`：Enabled、Mode=BLOCK\|ASYNC、Channels=SIGN\|SMS\|BOTH、适用卡类型位） |
| 签字 | A 写 `TB_TreatBillSignature` |
| 短信 | V1 可先做「开关+签字」；短信对接另切片（避免本模块绑死短信网关） |
| Block+创建即完成 | 与 Q1 冲突时：Block 开启则改为「待确认」状态，确认后才扣卡；或强制 Q1=二段 |

**重大：须与「创建即完成」模型一起确认。**

## 6. 本月内可取消 / 改经手人 / 改项目；隔月不可

### 已知

- `TB_TreatBillCancelProcess` **A** 可记取消审计。  
- 规则库 REF-002：已支付取消须退款；耗卡「已完成」接近已发生权益扣减。  
- 12 分析曾推荐 V1 不做 cancel——**被本诉求覆盖，须重锁**。

### 【业务歧义】

| 能力 | 风险 | 选项 |
|---|---|---|
| **取消** | 须回滚次数/储值 + 作废业绩 + CancelProcess；与退款模块重叠 | A：本月取消=系统内冲销（不走审批）；B：一律走退款审批（CONF-004）；C：本月快捷冲销+仍写退款单 |
| **改经手人** | 相对安全：改 Handler Scale + 业绩人 | 推荐本月允许；隔月禁 |
| **改项目** | 极高：旧权益加回、新权益重扣、耗材流水重算、业绩重写 | A：本月允许整单作废重开；B：允许改明细（复杂）；C：本月禁止改项目，仅改经手人/取消 |

### 时间窗

与补单一致：**自然月**（BillDate 或 CreatedOn？）

| 方案 | 含义 |
|---|---|
| **M1（推荐）** | 以 **BillDate** 所在自然月 = 今天所在月 可改 |
| M2 | 以 **CreatedOn** 所在月 |

### 建议锁定（推荐）

| 项 | 推荐 |
|---|---|
| 窗 | M1（BillDate 本月） |
| 改经手人 | 允许；权限 `treat:order:edit-handler` |
| 取消 | A 本月冲销回滚权益 + CancelProcess；**或** B 走退款——须拍板与 CONF-004 关系 |
| 改项目 | **C：V1 不直接改明细**；本月「取消后重开」满足业务，降低双扣风险 |

**须确认：取消 vs 退款；改项目是否禁止。**
