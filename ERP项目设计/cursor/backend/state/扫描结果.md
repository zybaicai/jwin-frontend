## 〇、差距总览（一句话）

现有系统 = **旧 SQL Server 库（约 906 表）+ 新 `com.yudao.erp` 适配层（部分域已通）+ 仓库内遗留 `com.mammon`（不启动）**。  
目标系统 = **模块化单体 ERP，完整覆盖组织/客户/商品卡项价格/销售/耗卡/权益/提成/退款，并满足业务规则库与权限模型**。

**最大差距**：商品·价格·渠道·活动管理几乎空白；销售/耗卡/退款有“写单骨架”但未按规则库验收；权限注解与测试严重不足。

## 四、数据层扫描（重点）

### 4.1 库规模

- `design/init.sql`：**约 906 张表**（旧业务库全量）
- ERP 增量（不在 init 或后补）：`TB_EmployeeJobType`、`TB_EmployeeOrgScope`、`TB_ErpCustomerFormField`、`TB_ErpSystemSetting`、权限种子、服务角色种子等（见 `db/erp_*.sql`）

### 4.2 核心表族（业务语义，非仅靠字段名）

结合《数据库设计》《业务领域模型》与现有 Service/XML：

| 表族 | 业务含义（文档+用法） | 主键习惯 | 备注 |
|---|---|---|---|
| `TK_Entity` | 组织树；`IsStore` 标记门店 | ID | 数据范围展开根 |
| `TK_Employee` / `TK_EmployeeEntity` | 员工及门店归属 | ID / 复合 | 人事 JobID ≠ 权限角色 |
| `TK_JobType` | 职务；现兼权限角色定义 | ID | 后续可拆角色表 |
| `TB_MenuPermission` / `TB_*MenuPermission` | 权限点与绑定 | Code / 复合 | 列名 `MenuPermissionCod` 历史缺字母 |
| `TB_Customer` / `TB_CustomerEntity` | 顾客主档 + 门店建档关系 | ID | 列表按当前店 Entity 过滤 |
| `TB_CustomerServicer` / `TB_Servicer*` | 护理角色与顾客绑定 | 复合 | |
| `TB_Project*` / `TB_Product*` | 项目/产品主数据与售卖/耗卡处理人、改价等 | ID | **管理端未建** |
| `TB_*Card` / `TB_*CardAccount` | 卡定义 vs 顾客账户 | ID | 定义与账户必须分离 |
| `TB_SaleBill*` | 销售主单/明细/支付/处理人/套餐展开 | 单号或 ID | 金额字段多，禁止混用 |
| `TB_TreatBill*` | 耗卡主单/明细/取消 | 单号 | 与销售独立事件 |
| `TB_Refund*` | 销退/耗退及明细流程 | 单号 | |
| `TB_*Performance*` / `*Commission*` | 业绩与提成（极多） | 复合 | 规则改后历史须快照 |
| `TB_PayMethod*` | 支付方式 | ID | 销售支付映射 |

**约束说明：** init 以业务表为主，外键未必在库层强制；语义外键靠代码维护。扫描不能只信列名（如 `Bill ID` 带空格、`MenuPermissionCod`）。

### 4.3 已有 Java DO 映射的表（20）

`TK_Entity, TK_Employee, TK_EmployeeEntity, TK_JobType, TB_Role, TB_EmployeeRole, TB_EmployeeLoginEntity, TB_MenuPermission, TB_RoleMenuPermission, TB_JobTypeMenuPermission, TB_EmployeeJobType, TB_EmployeeOrgScope, TB_Customer, TB_CustomerEntity, TB_TagLibrary, TB_CustomerTag, TB_CustomerSource, TB_ErpCustomerFormField, TB_Servicer, TB_ErpSystemSetting`

### 4.4 有 SQL/Service 使用但无 DO 的核心表（部分）

`TB_SaleBill*`、`TB_TreatBill*`、`TB_Refund*`、`TB_*Account`、`TB_Project`、`TB_Product`、`TB_*Card`、业绩表等 —— **通过 Mapper XML / 注解 SQL 直接访问**。

### 4.5 《现有数据库业务语义分析》（摘要原则）

1. **Bill 系表是交易事实**：金额、优惠、欠款、渠道、状态以开单当时为准，后续主数据变更不得回写污染。  
2. **Account 系表是权益余额**：次数/金额/本金赠金；耗卡与退款改账户须事务。  
3. **Card 定义表 ≠ Account**：卖的是定义，持有的是账户。  
4. **Performance/Commission 系是结果与规则**：计算后必须落快照，规则变更不影响历史。  
5. **组织范围增量表** `TB_EmployeeOrgScope`：配置勾选节点，运行时展开门店；**不能**用 `TK_EmployeeEntity` 替代权限范围。  
6. **禁止**用价格数值或名称推断渠道/卡类型（总规则 §6）。

## 九、《目标系统缺口清单》

### P0 核心业务缺失

1. **商品/项目完整管理**（分类、可售门店、处理人配置）  
2. **价格体系**（区域/活动/单店特价/生效期/后端重算）  
3. **销售渠道模型落地**（禁名称/价格推断）  
4. **四类卡定义管理 + 账户规则**（本金/赠金、跨店、有效期）  
5. **销售/耗卡/退款**相对《业务规则库》的正式验收与补齐（含事务、幂等、快照）  
6. **提成规则配置与历史快照**  
7. **关键接口 `@RequirePermission` 全覆盖 + 权限点扩充**

### P1 重要功能缺失

1. 顾客诊断/更完整会员等级运营  
2. 服务履约域（护理日志与耗卡金额分离）  
3. 退款审批流（若规则要求）  
4. 操作审计日志  
5. 自动化测试（登录范围、开单、耗卡、退款）  
6. 销售 Handler/业绩分摊与文档一致性核对  
7. state 台账维护（已完成模块、已确认库变更）

### P2 辅助功能缺失

1. 库存供应链 ERP 化  
2. 附件/签名/挂单等边缘表能力  
3. pom 清理与工程改名  
4. 管理端前端工程（本仓几乎无）

### P3 优化项

1. 为 Sale/Treat 补 DO/领域模型，减少纯 SQL 散落  
2. Repository 层补齐  
3. JWT secret/配置外置  
4. 双基线 mammon 隔离说明文档化
