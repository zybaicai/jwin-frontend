## 3. 当前架构

- **模块化单体**（与架构文档一致）
- **旧库适配**：直接映射 `TK_`* / `TB_*`，不另起新库
- 鉴权链：`AuthTokenFilter` → JWT → `PermissionLoader.enrich` → `@RequirePermission` AOP
- 统一响应：`ApiResult`；统一异常：`GlobalExceptionHandler` + `BizException` / `ErrorCodes`

## 5. 数据库访问方式

- MyBatis-Plus `BaseMapper` + 少量自定义 XML（如 `CustomerQueryMapper.xml`、`TkEmployeeMapper.xml`）
- DO 显式 `@TableField` 映射旧列名（含历史拼写如 `MenuPermissionCod`）
- 增量脚本：`db/erp_*.sql`（权限、组织范围、表单字段、服务角色、系统设置）
- 全量旧库：`design/init.sql` / `db/init.sql`（约 900+ 表，**禁止擅自改结构**）

## 12. 技术债

1. pom/artifact 仍叫 `mammon-merchant`，依赖混杂（云组件、支付、串口等）
2. 双代码基线（yudao + mammon）易混淆
3. `application-erp.properties` 含本地口令（弱口令占位）
4. 销售/耗卡/退款/提成实现深度与规则库未对齐验收
5. 权限注解覆盖不全；权限点未产品化全量清单
6. Repository 层名有设计、实现多直接 Mapper
7. 测试缺失；state 目录（已完成模块等）为空未维护
8. JWT secret 写死在配置

# AI研发上下文



## 永久遵守

1. `00-Cursor开发总规则` 全套
2. 优先级：**已确认业务规则 > 设计文档 > 现库 > 现码 > 任务 > AI 经验**
3. 不猜业务；歧义输出「业务歧义」模板并等待确认
4. 金额 `BigDecimal`；销售≠耗卡；价格/渠道不用名称推断
5. 历史快照不被新规则污染；财务操作事务化
6. 模块做完输出清单并**停止**，不自动开下一模块



## 数据库不能擅自改

- `design/init.sql` / 现网 `yudao` 中全部原业务表  
- 禁止未确认的删表/删字段/改语义/改类型/改默认值/改历史数据  
- 新增表字段须走：`08-数据库变更审查` → 人工确认 → 再执行  
- 已有增量（权限、组织范围等）视为已落地基线，再变更仍需审查



## 已存在模块

- 基础设施、认证会话  
- 组织 / 员工 / 职务 / 权限点 / 角色绑定 / 组织数据范围  
- 客户中心主路径  
- 商品查询、销售/耗卡/退款/业绩的接口骨架



## 缺失 / 薄弱模块

- E04 完整商品·卡项·价格·渠道·活动  
- E05～E09 按规则库完整实现与验收  
- 库存、审批、操作审计、完整权限矩阵、自动化测试、前端工程



## 当前应从哪里开始

建议顺序（对齐任务拆解依赖）：

```text
1）用 02/10 Prompt 验收并固化 E02 组织权限、E03 客户中心（补注解/文档/state）
2）再开 E04 商品与卡项（价格/渠道是销售前提）
3）然后 E05 销售 → E06/E07 权益耗卡 → E08 提成 → E09 退款
```

**本初始化阶段结论：不要立刻写新业务代码。**  
下一动作应由你指定：例如执行 `02-项目扫描`、对 E02/E03 做验收，或按 `12` 正式启动某一 Epic。
