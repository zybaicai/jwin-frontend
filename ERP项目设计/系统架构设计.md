# 一、系统架构设计目标

V1系统架构的第一目标不是追求：

- 微服务；
- 高并发；
- 极致性能；
- 最先进技术；
- 大而全平台化。

而是：

> **让一个3人左右的小团队，能够持续开发、持续维护，并且稳定替代原SaaS收银ERP。**

---

# 二、V1架构核心原则

## 原则1：模块化单体

V1不使用微服务。

采用：

> **Spring Boot模块化单体架构。**

---

## 原则2：旧数据库兼容

数据库不做大规模重构。

采用：

```Plain Text
新应用
 ↓
旧数据库适配层
 ↓
原有业务数据库
```

---

## 原则3：领域隔离

代码按业务领域分模块：

```Plain Text
customer
sale
treat
card
performance
inventory
refund
```

而不是所有代码都塞在：

```Plain Text
controller
service
mapper
```

三个大目录。

---



## 原则4：业务逻辑不能放Controller

Controller只负责：

```Plain Text
接收请求
参数校验
调用Application Service
返回结果
```

---



## 原则5：核心业务必须事务化

重点：

```Plain Text
销售
支付
办卡
耗卡
会员权益
退款
库存
业绩
```

---

# 四、为什么V1不采用微服务

你们目前团队：

```Plain Text
核心Java：1人
前端：1人
Java/DB：1人
```

如果直接微服务，会增加：

```Plain Text
网关
服务发现
配置中心
RPC
消息队列
分布式事务
链路追踪
多服务部署
多服务监控
```

但是目前真正困难的问题是：

```Plain Text
业务规则
旧库理解
销售
耗卡
卡项
绩效
退款
```

所以：

> **先把业务做对，比把系统拆碎更重要。**

# 九、Controller层

职责非常简单：

```Plain Text
HTTP
 ↓
DTO
 ↓
Application Service
```

例如：

```Java
@PostMapping("/orders/{id}/pay")
public Result<?> pay(
        @PathVariable Long id,
        @RequestBody PayOrderCommand command) {

    return Result.success(
        saleApplicationService.pay(id, command)
    );
}
```

Controller不要：

```Plain Text
查数据库
算余额
算提成
扣库存
```

# 三十六、第三方支付事务注意事项

这里不能简单：

```Plain Text
@Transactional
调用微信
更新数据库
```

因为：

> 数据库事务和第三方支付不是一个事务。

正确做法：

```Plain Text
创建支付单
 ↓
调用第三方
 ↓
等待回调/主动查询
 ↓
确认成功
 ↓
本地事务更新
```

---
