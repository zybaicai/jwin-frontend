# 一、Cursor 工作总原则

Cursor 在任何开发任务开始前，必须遵守以下原则。

## 1. 禁止直接凭经验设计业务

开发任何功能前必须先检查：

1. 当前项目已有代码
2. 当前项目已有 Entity
3. 当前项目已有数据库表
4. 当前项目已有 SQL
5. 当前项目已有 API
6. 当前项目已有业务逻辑
7. 当前项目已有枚举
8. 当前项目已有权限模型

# 二、数据库第一原则

本项目已有数据库，并且数据库数据已经被BI系统使用。

因此数据库设计遵循：

```text
旧表能实现
    ↓
直接使用旧表

旧表字段不足
    ↓
优先增加字段

旧表完全无法表达
    ↓
新增扩展表

只有旧逻辑严重错误且无法兼容
    ↓
提出数据库变更方案
    ↓
等待人工确认
```

Cursor 不得自行：

- 删除旧表
- 修改旧字段含义
- 大规模拆表
- 大规模合并表
- 重命名旧字段
- 修改历史数据结构
- 修改BI依赖字段
- 删除原有业务字段

如果认为必须改变数据库结构，必须先说明：

```text
现有结构：
为什么无法满足：
建议改动：
影响的旧逻辑：
影响的BI：
迁移方案：
是否可以通过新增表解决：
```

未经人工确认，不得执行破坏性数据库修改。

# 五、最核心的业务概念



## 5.1 标准项目

标准项目是公司的统一服务项目定义。

例如：

```text
项目编码：XM001
项目名称：头疗60分钟
标准原价：999
```

一个标准项目只能有一个业务身份。

美团项目、团购项目、普通项目不能因为价格不同而创建成三个项目。

必须：

```text
美团头疗60分钟
        ↓
project_id = XM001

普通销售头疗60分钟
        ↓
project_id = XM001

团购头疗60分钟
        ↓
project_id = XM001
```

这样才能保证BI统计统一。

# 六、项目分类

项目分类允许总部配置。

支持：

```text
一级分类
二级分类
项目
```

分类允许新增、修改、停用。

项目允许新增。

禁止通过删除项目破坏历史订单。

---



# 七、项目改名规则

项目改名以后：

### 新订单

使用新名称。

### 历史订单

原则上显示订单成交时保存的项目名称。

### 历史客户卡

原则上显示售卡时保存的项目名称。

因此订单明细和客户卡项必须保存项目名称快照。

至少：

```text
project_id
project_name
```

不能只依赖当前项目表名称。

---



# 八、销售方式模型

系统需要支持多个销售方式。

默认包括：

```text
普通销售
美团
团购
```

未来允许新增：

```text
抖音
小红书
其他平台
公司活动
特殊渠道
```

销售方式不能写死在Java代码中。

应该配置化。

---



# 九、收银员必须主动选择销售方式

系统不能根据订单自动猜测销售渠道。

正确流程：

```text
开单
 ↓
选择销售方式
 ↓
选择项目
 ↓
系统显示该销售方式当前有效价格
 ↓
收银员确认
 ↓
允许时可改价
 ↓
提交订单
```

例如：

```text
普通销售       198
美团           159
团购           149
```

由收银员选择。

# 十、销售方式可用范围

不是所有门店都可以使用所有销售方式。

需要判断：

```text
门店

销售方式
+
当前时间
+
状态
```

例如：

```text
杭州A店：
普通销售 √

```

```text
启用时间
停用时间
适用门店
状态
```

# 十一、价格体系

项目标准原价与实际销售价格必须分离。

例如：

```text
项目：
头疗60分钟

标准原价：
999
```

实际价格可以：

```text
普通销售：699
美团：599
团购：499
统一活动：399
单店特殊价格：299
```

标准项目表不得增加：

```text
meituan_price
group_price
first_tier_price
second_tier_price
```

这种大量固定价格字段。

必须采用配置关系。

---



# 十二、区域价格

系统支持价格区域。

例如：

```text
全国
一线市场
二线市场
```

门店属于某个价格区域。

普通销售价格可以：

```text
一线市场：699
二线市场：599
```

储值卡折扣也使用价格区域。

---



# 十三、价格版本

标准价格支持版本。

例如：

```text
2026标准价格
2027标准价格
```

每个价格版本必须有：

```text
version_code
version_name
start_time
end_time
status
```

价格调整后：

> 已成交订单不得跟随新价格变化。

订单必须保存成交时价格快照。

---



# 十四、价格规则

项目价格至少包含：

```text
project_id
sale_channel_id
price_area_id
price_version_id
price
```

必要时增加：

```text
min_price
status
start_time
end_time
```

价格规则必须支持有效时间。

---



# 十五、价格优先级

标准价格匹配时：

```text
这个价格没有优先级，是按照前端用户选择项目，渠道对应展示对应价格
```

但是：

> 套餐卡、通用次卡、时效卡属于独立卡类商品，其项目金额来自卡类商品设计，不参与普通项目价格匹配。

储值卡属于动态消费价格体系。

# 十八、特殊价格审批

门店不能直接突破总部价格体系。

正确流程：

```text

 ↓

 ↓
填写申请价格
 ↓
填写原因
 ↓
提交审批
 ↓

 ↓
审批通过
 ↓
生成特殊价格规则
 ↓
开始生效
```

# 十九、改价权限

“特殊价格”和“临时改价”是两个概念。

特殊价格：

> 总部事先给门店配置一个特殊销售价格。

改价：

> 收银过程中，在标准价格基础上临时调整成交价格。

---



# 二十、改价权限必须配置化

总部可以控制：

```text
哪些门店允许改价
哪些项目允许改价
哪些销售方式允许改价
最大优惠幅度
最低成交价格
是否需要审批
```

例如：

```text
杭州A店
头疗60分钟
美团

允许改价：是
最低价格：139
```

那么：

```text
标准价：159
允许：
159 → 150
159 → 140

禁止：
159 → 99
```

---



# 二十一、改价原因

改价必须支持原因。

例如：

```text
美团优惠券
顾客特殊情况
平台补贴
门店引流
总部特批
其他
```

如果是自由输入，也必须保存备注。

# 二十二、订单必须保存价格快照

订单明细至少保存：

```text
project_id
project_name
sale_channel_id
sale_channel_name
price_rule_id
standard_price
original_sale_price
discount_amount
final_unit_price
quantity
amount
is_price_changed
price_change_reason
operator_id
```

其中：

```text
standard_price
```

是项目原价。

```text
original_sale_price
```

是正常应该收的价格。

```text
final_unit_price
```

是实际成交价格。

# 二十三、卡类商品

系统支持：

```text
单独卖项目
通用次卡
时效卡
储值卡
套餐卡
```

---



# 二十四、单独卖项目

例如：

```text
头疗60分钟
标准原价：999

普通销售：
699
```

实际销售：

```text
销售金额 = 699
```

---



# 二十五、通用次卡

通用次卡在设计阶段确定：

```text
卡售价
包含项目
项目数量
每个项目的售卖/耗卡价值
```

例如：

```text
通用头疗卡
售价：999

头疗60分钟 × 10
单次价值：99
```

客户购买后：

```text
卡项价格 = 99
```

以后消费：

```text
耗卡金额 = 99
```

不得重新读取当前项目价格。

---



# 二十六、时效卡

时效卡同样在设计阶段确定：

```text
卡售价
有效期
项目
次数/使用规则
项目价值
```

例如：

```text
30天头疗卡
售价：999

头疗60分钟
单次耗卡：99
有效期：30天
```

消费：

```text
耗卡金额 = 99
```

---



# 二十七、套餐卡

套餐卡设计阶段确定：

```text
套餐售价
套餐项目
数量
每个项目单次价值
```

例如：

```text
尊享养护卡
售价：1999

头疗60分钟 × 10
99/次

肩颈护理 × 5
80/次
```

---



# 二十八、套餐卡售出后必须形成价格快照

这是强制规则。

客户购买套餐卡以后：

```text
套餐模板
       ↓
复制项目
       ↓
复制数量
       ↓
复制项目金额
       ↓
形成客户卡项快照
```

以后套餐模板价格修改：

> 已经售出的客户卡不得改变。

---



# 二十九、套餐卡退款

套餐卡项目可以单独退款。

退款金额按照客户卡项剩余价值计算。

例如：

```text
头疗60分钟
原始10次
单次99

已经消费3次

剩余7次
剩余项目价值：
7 × 99 = 693
```

具体退款规则必须使用客户卡项快照。

禁止使用当前套餐模板价格重新计算历史卡退款。

---



# 三十、储值卡

储值卡与其他卡不同。

储值卡：

```text
充值金额 = 本金余额
```

默认充值单位：

```text
1000
```

例如：

```text
充值1000
充值2000
充值3000
```

本金与赠金如果原系统已经存在对应逻辑，必须继续保持分离。

---



# 三十一、储值卡消费价格

储值卡消费采用：

```text
项目原价 × 当前区域储值卡折扣
```

例如：

一线市场：

```text
项目原价：1000
储值卡折扣：5折
耗卡金额：500
```

二线市场：

```text
项目原价：1000
储值卡折扣：4折
耗卡金额：400
```

---



# 三十二、储值卡折扣配置

总部可以配置：

```text
价格区域
项目
储值卡折扣
有效时间
```

例如：

```text
一线市场
头疗60分钟
5折

二线市场
头疗60分钟
4折
```

折扣不得由门店随意修改。

---



# 三十三、储值卡消费必须记录计算依据

储值卡消费记录至少保存：

```text
project_id
project_name
standard_price
price_area_id
discount_rate
consumption_amount
```

这样历史数据可以追溯：

```text
原价1000
一线市场
5折
实际耗卡500
```

即使以后总部把折扣从5折改成4.5折：

> 历史消费仍然保持500。

---



# 三十四、销售与耗卡是两个独立业务事件

销售：

```text
客户付款
 ↓
产生销售记录
```

耗卡：

```text
客户消费
 ↓
产生耗卡记录
```

二者不得合并。

---



# 三十五、销售金额

销售金额以实际收款金额为核心。

例如：

```text
项目原价999
实际销售699

销售金额 = 699
```

---



# 三十六、耗卡金额

次卡/时效卡/套餐卡：

```text
耗卡金额 = 售卡时确定的项目金额
```

储值卡：

```text
耗卡金额 = 当前项目原价 × 当前储值卡折扣
```

---



# 三十七、团购立即消费

例如：

```text
团购售价159
当天立即消费
```

系统产生：

```text
销售金额 = 159

耗卡金额 = 159
```

但是：

```text
不是销售金额 = 318
```

而是：

```text
销售业务：
159

耗卡业务：
159
```

两个业务统计维度独立。

---



# 三十八、销售提成

销售提成：

> 不使用阶梯。

销售提成按照：

```text
项目
+
销售方式
+
角色
```

配置。

例如：

```text
头疗60分钟
普通销售

员工：5%
店长：2%
区级：1%
```

美团可以：

```text
员工：3%
店长：1%
区级：0.5%
```

---



# 三十九、销售提成计算

例如：

```text
实际销售金额：699
员工提成：5%
```

则：

```text
销售提成 = 699 × 5%
```

如果订单实际改价：

```text
699 → 599
```

提成按照最终业务规定的实际销售金额计算。

默认：

```text
599 × 5%
```

---



# 四十、消耗提成

消耗提成与销售提成完全独立。

消耗提成支持：

```text
角色
等级
业绩区间
提成比例
```

例如：

```text
月耗卡0~30000：
员工2%
店长1%
区级0.5%

月耗卡30000~50000：
员工3%
店长1.5%
区级0.8%

月耗卡50000以上：
员工4%
店长2%
区级1%
```

所有规则前端可配置。

---



# 四十一、提成规则必须支持版本/有效期

提成规则修改后：

> 历史已经计算完成的提成不得因为新规则变化而变化。

因此提成计算记录必须保存：

```text
commission_rule_id
commission_rate
commission_base_amount
commission_amount
```

# 八十四、系统核心原则总结

整个系统必须围绕以下几个核心原则开发：

```text
原则1：
一个标准项目只有一个业务身份。

原则2：
渠道不是项目。

原则3：
价格不是项目属性，而是配置规则。

原则4：
收银员主动选择销售方式。

原则5：
系统展示当前门店当前时间可用的销售方式。

原则6：
门店默认按照总部价格销售。

原则7：
特殊价格必须经过总部/区域授权。

原则8：
临时改价必须受权限、项目、门店、渠道、金额范围控制。

原则9：
订单保存成交价格快照。

原则10：
已售卡项保存项目金额快照。

原则11：
销售和耗卡是两个独立业务事件。

原则12：
销售提成按角色配置，不使用等级制。

原则13：
消耗提成按角色+等级配置。

原则14：
储值卡按照当前区域折扣动态计算消费金额。

原则15：
通用次卡、时效卡、套餐卡按照售卡时固定的项目金额消费。

原则16：
价格调整不影响历史业务。

原则17：
尽量复用原数据库。

原则18：
数据库无法表达时才增加字段/表。

原则19：
涉及金额的业务必须事务化。

原则20：
所有核心业务必须可审计、可追溯。
```
