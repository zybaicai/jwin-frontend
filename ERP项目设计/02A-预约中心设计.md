# 养发直营连锁 ERP

# 预约中心业务与研发设计 V1.0

---

# 1. 文档定位

预约中心是养发直营连锁 ERP 中独立的业务中心。

预约中心的核心目的不是单纯记录“客户几点来”。

而是通过：

```text
门店
+
员工
+
护理师
+
排班
+
可服务时间
+
跨店支援
+
项目服务时长
+
预约数量
+
预约状态
```

形成门店实时可用服务能力。

最终实现：

```text
门店排班
    ↓
计算护理师可服务时间
    ↓
计算当前可预约能力
    ↓
客户选择项目/时间
    ↓
创建预约
    ↓
锁定护理师时间
    ↓
到店确认
    ↓
完成服务
```

预约中心必须成为：

**门店服务产能管理中心。**

---

# 2. 预约中心解决的问题

系统需要解决：

## 2.1 门店今天有多少护理师

例如：

```text
杭州XX店

护理师A：早班
护理师B：早班
护理师C：晚班
护理师D：休息
护理师E：跨店支援
```

系统应该能够自动计算：

```text
当前时段实际可服务护理师：
A
B
E
```

---

# 2.2 哪些时间可以预约

不是所有时间都可以预约。

例如：

```text
护理师A：

09:00 - 18:00

护理师B：

09:00 - 18:00

护理师C：

13:00 - 22:00
```

那么：

```text
09:00 - 13:00
可用护理师：A、B

13:00 - 18:00
可用护理师：A、B、C

18:00 - 22:00
可用护理师：C
```

系统根据排班自动计算预约能力。

---



# 2.3 项目需要占用多长时间

预约不是只记录：

```text
14:00
```

而必须记录：

```text
开始时间
+
结束时间
+
服务时长
```

例如：

```text
头疗护理
14:00
60分钟
```

则占用：

```text
14:00 - 15:00
```

如果：

```text
染护项目
14:00
120分钟
```

则占用：

```text
14:00 - 16:00
```

因此：

**项目服务时长是预约容量计算的重要基础数据。**

# 4. 核心领域模型

预约中心核心领域：

```text
门店
  ↓
护理师
  ↓
排班
  ↓
可用时间
  ↓
服务能力
  ↓
预约
```

核心聚合：

## 4.1 门店排班聚合

```text
StoreSchedule
    |
    ├── EmployeeSchedule
    ├── Shift
    └── CrossStoreSupport
```

负责：

```text
谁上班
谁休息
谁早班
谁晚班
谁跨店支援
```

---



# 5. 护理师与排班

预约能力的最底层不是预约本身。

而是：

**护理师可用时间。**

---



## 5.1 排班

一个护理师每天可以拥有：

```text
早班
晚班
休息
其他班次
```

例如：

```text
张三

2026-09-16
09:00 - 18:00
```

---



## 5.2 休息

如果：

```text
张三
2026-09-16
休息
```

则：

```text
张三
当天不可预约
```

---



## 5.3 跨店员工

一个护理师可以属于A店。

但某一天：

```text
张三
原所属门店：A店

2026-09-16
支援：B店

工作时间：
13:00 - 22:00
```

那么当天：

```text
B店可预约护理师
+
1
```

而A店：

```text
当天不能继续把张三作为可预约护理师
```

因此跨店支援必须被视为：

**特定日期的排班能力变更。**

不能简单修改员工所属门店。

员工主数据中的：

```text
employee.storeId
```

不能因为跨店支援而修改。

应该通过：

```text
CrossStoreSupport
```

或者等价的排班记录表达。

---



# 6. 护理师可预约能力

系统必须建立一个：

```text
Availability
```

概念。

其含义：

> 某个门店、某个日期、某个时间段，可以安排多少护理师提供服务。

例如：

```text
2026-09-16
14:00 - 15:00

杭州XX店

可用护理师：
张三
李四
王五
```

则：

```text
availableCapacity = 3
```

---



# 7. 可预约能力不能简单等于上班人数

例如：

```text
张三：
09:00-18:00

李四：
09:00-18:00

王五：
13:00-22:00
```

现在已经存在：

```text
14:00-15:00
张三预约
```

那么：

```text
14:00-15:00

剩余可用：
李四
王五
```

所以：

```text
排班能力
-
已经被预约占用的时间
=
剩余预约能力
```

---



# 8. 项目服务时长

每个标准项目必须能够配置：

```text
serviceDuration
```

例如：

```text
头疗护理：60分钟
头皮检测：30分钟
深层护理：90分钟
```

项目服务时长可以随着业务变化进行配置。

---



# 9. 项目与预约时长

预约创建时：

```text
projectId
```

确定项目。

系统读取：

```text
项目服务时长
```

得到：

```text
duration
```

最终形成：

```text
startTime
endTime
duration
```

---



# 10. 历史预约时长快照

如果项目：

```text
原来60分钟
```

后来修改成：

```text
90分钟
```

历史预约不能自动变成：

```text
90分钟
```

因此预约必须保存：

```text
projectId
projectNameSnapshot
serviceDurationSnapshot
```

历史预约按照创建时的项目服务时长保留。

# 12. 顾客

预约可以关联顾客。

```text
customerId
```

顾客不是预约的唯一前提。

具体是否允许：

```text
无会员预约
```

由业务规则进一步确定。

如果当前业务要求预约必须关联顾客：

则创建预约时：

```text
customerId 必填
```

如果允许匿名预约：

则：

```text
customerId nullable
```

此规则必须最终在业务规则库中明确。

---



# 13. 护理师

预约必须明确护理师：

```text
employeeId
```

因为预约实际上是：

> 给某一个护理师锁定一个时间段。

因此预约核心冲突条件：

```text
同一护理师
+
时间重叠
```

必须阻止。

---



# 14. 预约类型

预约必须具备：

```text
appointmentType
```

用于区分预约来源/性质。

具体枚举不能由 Cursor 自行扩展。

当前可以设计为可扩展结构，例如：

```text
普通预约
客户预约
门店预约
其他业务预约
```

实际类型以最终业务规则为准。

---



# 15. 预约状态

预约必须使用明确状态。

至少支持：

```text
待确认
已确认
未到店
已到店
已完成
已取消
```

具体是否增加：

```text
已改期
服务中
爽约
```

必须根据最终业务确认。

---



# 16. 状态流转

推荐状态模型：

```text
待确认
   │
   ├── 确认 → 已确认
   │
   └── 取消 → 已取消

已确认
   │
   ├── 到店 → 已到店
   │
   ├── 未到店 → 未到店
   │
   └── 取消 → 已取消

已到店
   │
   └── 服务完成 → 已完成
```

原则：

不能任意修改状态。

必须通过状态机控制。

例如：

```text
已完成
```

不能直接：

```text
→ 待确认
```

除非存在明确的特殊业务流程。

---



# 17. 预约取消

单个预约允许取消。

取消必须：

```text

+
记录取消人
+
取消时间
+
取消原因
```

不能直接删除预约记录。

原则：

**预约历史必须保留。**

# 18. 预约修改

单个预约允许修改。

可修改内容包括：

```text

护理师
```

但修改必须重新校验：

```text

```

# 19. 修改预约的核心原则

例如：

原预约：

```text

14:00-15:00
```

```text

```

```text

```

# 27. 可预约时间计算

系统核心算法：

```text
第一步：
读取门店当天排班

第二步：
读取护理师当天排班

第三步：
处理休息

第四步：
处理跨店支援

第五步：
获取护理师已有预约

第六步：
获取项目服务时长

第七步：
计算可插入时间段

第八步：
返回可预约能力
```

---



# 28. 可预约时间不能由前端自行计算

前端可以展示：

```text
09:00
10:00
11:00
```

但是：

**最终是否可以预约必须由后端判断。**

因为用户可能同时打开两个页面。

例如：

```text
A收银员看到：
14:00可预约

B收银员同时预约：
14:00
```

A随后提交。

后端必须再次检查。

---



# 29. 预约并发控制

核心场景：

```text
护理师张三
14:00-15:00
```

同时：

```text
收银员A创建预约
收银员B创建预约
```

系统必须保证：

**最多只有一个预约成功。**

不能出现：

```text
张三
14:00-15:00

预约A
预约B
```

两个同时成功。

---



# 30. 预约冲突规则

冲突判断：

```text
同一门店
+
同一护理师
+
预约时间发生重叠
```

即冲突。

时间重叠判断：

```text
newStart < existingEnd
AND
newEnd > existingStart
```

例如：

已有：

```text
14:00-15:00
```

新预约：

```text
14:30-15:30
```

冲突。

新预约：

```text
15:00-16:00
```

不冲突。

---



# 31. 项目服务时长影响预约

例如：

护理师：

```text
14:00-16:00
```

项目A：

```text
60分钟
```

则：

```text
14:00
15:00
```

都可能作为开始时间。

如果项目B：

```text
90分钟
```

则：

```text
14:00
```

可以。

但：

```text
15:00
```

可能无法安排，因为：

```text
15:00-16:30
```

超出护理师可服务时间。

# 39. 预约与销售的关系

预约本身：

**不是销售订单。**

预约：

```text
客户要来
```

销售：

```text
客户付款
```

两者必须分离。

可能出现：

```text
预约
↓
到店
↓
销售
```

也可能：

```text
预约
↓
到店
↓
直接耗卡
```

因此预约不能直接等同于销售。

---



# 40. 预约与耗卡的关系

预约：

```text
服务安排
```

耗卡：

```text
实际消费
```

因此：

```text
预约成功
≠
已经耗卡
```

```text
已到店
≠
已经耗卡
```

只有实际发生服务消费时：

```text
预约
↓
到店
↓
实际服务
↓
耗卡
```

才产生耗卡业务。

---



# 41. 预约与项目

预约必须关联标准项目：

```text
projectId
```

不能：

```text
projectName
```

作为业务主键。

项目名称修改以后：

历史预约保留：

```text

```

---



# 42. 预约与护理师

预约必须关联：

```text
employeeId
```

但护理师当天能否服务：

不能仅仅根据：

```text
employee.storeId
```

判断。

必须综合：

```text
员工所属门店
+
当天排班
+
跨店支援
+
休息
+
已有预约
```

---



# 43. 跨店支援规则

跨店支援必须具有：

```text
sourceStoreId
targetStoreId
employeeId
supportDate
startTime
endTime
status
```

例如：

```text
张三

原门店：
A店

B店

2026-09-16

```

系统应将：

```text

```


# 79. 核心设计原则总结

预约中心最终不是：

```text
appointment CRUD
```

而是：

```text
排班管理
+
服务能力计算
+
护理师时间管理
+
项目时长管理
+
预约管理
+
预约状态管理
+
跨店支援
+
预约看板
+
到店履约
```

其核心业务价值：

> **让系统根据门店真实排班和护理师实时可用时间，自动判断某个项目、某个时间段还能不能预约。**

最终形成：

```text
“门店有多少护理师”
        ↓
“今天谁上班”
        ↓
“谁在别的店支援”
        ↓
“谁正在被预约”
        ↓
“这个项目需要多久”
        ↓
“这个时间还能不能安排”
        ↓
“能安排几个护理师”
```

这才是预约中心的核心。
