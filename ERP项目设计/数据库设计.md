# 数据库设计

下面进入 **07《数据库设计 V1\.0——旧数据库兼容映射版》**。

这一章和普通项目的数据库设计完全不同。

我们已经明确：

> **V1\.0 不重构旧数据库。**
> 
> 

所以这里不做“重新建多少张新表”的设计，而是做：

> **业务领域模型 → 旧数据库真实表 → 字段语义 → 读写职责 → 事务边界 → BI影响 → Java Repository适配**
> 
> 

我已经对你提供的 `丝域新系统表结构.xlsx` 做了实际结构分析：旧库共 **906 张表**，字段结构共 **6676 行**。旧库明显已经形成 `TB / TK / TE / TM / TS` 多类业务表体系，其中销售、消耗、卡项、退款、绩效、提成、员工、库存都有非常完整的业务族群。

因此这一次我们不“嫌旧库复杂而重新设计”，而是把这套旧数据库当成：

# V1\.0的业务数据底座

# 一、V1\.0数据库总原则

## DB\-001：旧数据库结构作为V1事实底座

原则：

> **不因为新系统开发而主动改变既有核心表结构。**
> 
> 

包括：

- 不随意改表名；

- 不随意删字段；

- 不随意改字段类型；

- 不随意改变字段原有含义；

- 不随意改变主键关系；

- 不随意删除历史数据；

- 不破坏BI依赖字段。

---

# 二、为什么这次不重构906张表

旧库虽然表很多，但是这些表已经经过实际门店经营验证。

尤其：

```Plain Text
TB_SaleBill*
TB_TreatBill*
TB_SavingCard*
TB_PackageCard*
TB_GeneralCard*
TB_TimeCard*
TB_Refund*
TB_*Performance*
TK_*Commission*
TE_*
```

这些已经形成了：

> 公司实际业务规则的数据库表达。
> 
> 

如果现在重新做数据库：

```Plain Text
旧库
 ↓
新库
 ↓
数据迁移
 ↓
BI重新适配
 ↓
新ERP
```

等于同时启动：

```Plain Text
ERP重开发
+
数据迁移
+
BI改造
```

项目风险和成本都会大幅增加。

# 五、数据库表分类

从旧库结构看，可以按照业务职责理解为：

```Plain Text
TB
→ 核心业务交易/基础业务表

TK
→ 配置、规则、绩效、提成、员工等管理类数据

TE
→ 门店库存、采购、供应链、收付款等经营类数据

TM
→ 小程序/商城/预约等扩展业务

TS
→ 系统/辅助数据
```

这里不是要求程序代码按表前缀划分，而是用于我们逆向理解旧数据库。

# 四十、数据库并发控制
